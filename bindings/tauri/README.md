# kevy for Tauri v2

Embed **kevy** — the pure-Rust, zero-dependency, Redis-compatible engine —
directly in a Tauri v2 app's Rust backend, and drive it from the webview.

A Tauri backend *is* Rust, so kevy needs no server, no socket, and no separate
process: the plugin holds one [`kevy_embedded::Store`](../../crates/kevy-embedded)
in Tauri's managed state and exposes it to JS over `invoke`. One shared store
lives in the Rust process — every webview call and every Rust-side call see the
same keyspace and the same pub/sub bus.

```
bindings/tauri/
├── tauri-plugin-kevy/   # the Tauri v2 plugin crate (standalone — see boundary note)
├── guest-js/            # typed webview client over invoke  (npm: tauri-plugin-kevy-api)
└── example/             # a minimal runnable app: set/get + live pub/sub
```

## What you get

| Command (`plugin:kevy|…`) | Purpose |
|---|---|
| `cmd(argv)` | run **any** of kevy's ~184 verbs by argv; returns the decoded RESP reply |
| `get` / `set` / `del` / `exists` / `incr` | typed scalar fast paths |
| `ping` / `dbsize` / `flushall` | keyspace basics |
| `publish` / `subscribe` / `unsubscribe` | pub/sub, streamed to the webview over a Tauri `Channel` |

The raw `cmd` path is the escape hatch that keeps every engine capability
(hash / list / set / zset / `IDX.*` / `VIEW.*` / `FEED.*` / …) reachable from
JS without a per-verb command — mirroring the
[client contract](../../docs/client-contract.md) §3.

## Install

**1. Rust — add the plugin to your app's `src-tauri/Cargo.toml`:**

```toml
[dependencies]
tauri-plugin-kevy = { path = "../../bindings/tauri/tauri-plugin-kevy" }
# or, once published: tauri-plugin-kevy = "6"
```

**2. Register it** in `src-tauri/src/lib.rs`:

```rust
tauri::Builder::default()
    // In-memory (nothing survives the process):
    .plugin(tauri_plugin_kevy::init())
    .run(tauri::generate_context!())
    .expect("run tauri app");
```

Persistent (snapshot + AOF, restart-safe), or sharing a store your Rust code
also holds a clone of:

```rust
use tauri_plugin_kevy::{Builder, Store, Config};

// Snapshot + AOF under an app-data dir:
.plugin(tauri_plugin_kevy::Builder::new().path(app_data_dir).build())

// …or hand the plugin a Store your Rust code keeps a handle to
// (Store is Clone — a cheap Arc bump; both see the same keyspace):
let store = Store::open(Config::default().with_persist("./data"))?;
your_state.kevy = store.clone();
// .plugin(Builder::new().store(store).build())
```

**3. Grant the permission** in `src-tauri/capabilities/default.json`:

```json
{
  "identifier": "default",
  "windows": ["main"],
  "permissions": ["core:default", "kevy:default"]
}
```

`kevy:default` grants the full command surface (embedded kevy is a local,
in-process store with no auth boundary). For a read-only webview, drop it and
list individual `kevy:allow-get` / `kevy:allow-exists` / `kevy:allow-ping`
permissions instead — each is autogenerated from the plugin's `build.rs`.

**4. (Optional) install the typed JS client:**

```bash
npm install tauri-plugin-kevy-api   # from bindings/tauri/guest-js
```

## Invoke from JS

With the typed client:

```ts
import { kevy, replyInt } from 'tauri-plugin-kevy-api'

await kevy.set('greeting', 'hello')
await kevy.getString('greeting')            // "hello"
await kevy.incr('counter')                  // 1

// Typed families ride the raw path:
await kevy.hset('user:1', 'name', 'ada', 'age', '36')  // 2
await kevy.lpush('log', 'a', 'b')                       // 2

// Any verb via the raw escape hatch:
const reply = await kevy.cmd(['ZADD', 'board', '10', 'ada'])
replyInt(reply)                             // 1

// Live pub/sub — frames stream over a Tauri Channel:
const sub = await kevy.subscribe({ channels: ['room'] }, (m) => {
  if (m.kind === 'message') console.log('got', m.payload)
})
await kevy.publish('room', 'ping')
// …later:
await sub.unsubscribe()
```

Or without the client, using the global (needs `withGlobalTauri`), exactly as
the [example app](./example) does:

```js
const { invoke, Channel } = window.__TAURI__.core
const bytes = (s) => Array.from(new TextEncoder().encode(s))
await invoke('plugin:kevy|set', { key: bytes('k'), value: bytes('v'), ttlMs: null })
```

Keys and values cross the IPC boundary as **byte arrays** (`number[]`), so all
data is binary-safe — the client packs `string` / `Uint8Array` for you, and
decodes reply bytes back to `Uint8Array` / `string` via the `reply*` helpers.

## Shared store (this plugin) vs. wasm-in-webview

kevy offers **two** doors into a Tauri app. Pick by where the data must live.

| | **Shared store** (this plugin) | **wasm in the webview** ([`kevy-wasm`](../../crates/kevy-wasm)) |
|---|---|---|
| Where kevy runs | Rust backend (native) | inside the webview (WASM) |
| Shared across windows / with Rust | **Yes** — one store, one bus | No — each webview is its own isolated store |
| Persistence | snapshot + AOF on disk | ephemeral (or you wire your own IndexedDB dump/load) |
| Performance | native speed, one IPC hop per call | in-VM, no IPC, but WASM speed |
| Reaches Rust-side state / files / replication | Yes | No |
| Best for | the app's real data store, cross-window state, durable caches, pub/sub between windows | a sandboxed, throwaway store scoped to one webview; offline demos; per-view scratch space |

**Rule of thumb:** if the data is the app's, or more than one window/Rust touches
it, or it must survive a restart → the shared store (this plugin). If it's
private scratch space for a single webview and must never leave it → wasm.
You can use both: durable app data in the backend store, ephemeral view-local
state in wasm.

## The 0-dependency workspace boundary (why this crate is "outside")

kevy's core workspace is **strictly 0-dependency** — only `std` and the
`kevy-*` crates, no crates.io deps (even the N-API / JNI doors hand-write their
FFI rather than pull the `napi` / `jni` crates). A Tauri plugin *unavoidably*
depends on the `tauri` crate (for `#[tauri::command]`, `Runtime`, `Builder`).

So `tauri-plugin-kevy` is **deliberately NOT a member of the kevy root Cargo
workspace**. It lives in the root `Cargo.toml` `exclude` list and carries its
own empty `[workspace]` table, so `cargo build` at the repo root never pulls
`tauri` into the 0-dep graph. This is the honest ecosystem boundary — exactly
where a real user's Tauri app sits: the app's `src-tauri` depends on `tauri`,
and so does this plugin. The engine it embeds, `kevy-embedded`, stays 0-dep.

```toml
# root Cargo.toml
[workspace]
members = [ … ]     # tauri-plugin-kevy is NOT here
exclude = [
    "bindings/tauri/tauri-plugin-kevy",
    "bindings/tauri/example/src-tauri",
]
```

The plugin path-depends on two 0-dep workspace crates and reuses them rather
than reimplementing anything:
- [`kevy-embedded`](../../crates/kevy-embedded) — the in-process `Store`.
- [`kevy-resp`](../../crates/kevy-resp) — decodes the raw `cmd` RESP reply
  (its `parse_reply`), so `cmd` returns a structured `Reply`, not opaque bytes.

## Build & test

```bash
# The plugin: unit + integration tests (headless — no webview).
cd bindings/tauri/tauri-plugin-kevy && cargo test

# The guest client: typecheck.
cd bindings/tauri/guest-js && npm install && npm run typecheck

# The example app (needs the Tauri prerequisites + @tauri-apps/cli):
cd bindings/tauri/example && npm install && npm run dev
```

The plugin's `cargo test` exercises the store-backed logic of every command
against a live embedded store, the RESP→JSON reply decoding, the pub/sub bridge
end-to-end over a real Tauri `Channel`, and headless plugin registration under
Tauri's `MockRuntime`. A full `tauri build` (webview bundle + WebKit) is out of
scope for `cargo test`; the example app is the vehicle for that.
