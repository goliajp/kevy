Realtime

Push it to everyone
who is listening

Chat, presence, notifications, a dashboard that updates itself. One publish, many subscribers, no polling. And in the browser build, the same pub/sub works between two tabs with no server at all.

Why this fits — and where it does not

Pub/sub is fire-and-forget. A message goes to whoever is subscribed at that moment; nobody who connects a second later will ever see it, and there is no acknowledgement. That is exactly right for a presence ping or a live counter, and exactly wrong for anything you would be upset to lose.

If losing a message matters, use a stream instead — see queues. Streams keep history, support consumer groups, and let a client that was offline catch up. Pub/sub is the cheap thing; the cheapness is the trade.

Fan a message out to everyone listening

One publish reaches every subscriber connected at that moment — a chat room, a notification, a live counter.

  1. Each client subscribes

    PSUBSCRIBE takes a whole family of channels on one connection.

    SUBSCRIBE room:42
PSUBSCRIBE room:*          # every room, one connection

  2. Publish — the reply is the audience

    PUBLISH room:42 '{"user":"ada","text":"hello"}'
-> (integer) 3             # how many subscribers received it
Cost & limits

A slow subscriber is dropped, not buffered forever. If a client cannot keep up, its messages are discarded rather than growing the server's memory without bound — a deliberate choice, and one to know about before you rely on delivery. No acknowledgement, no replay: if either matters, you want a stream, not a channel. The pub/sub guide is specific about the limits.

Presence — who is online right now

The engine's expiry does the bookkeeping: a client that goes silent falls off the roster by itself.

  1. Heartbeat: a key with a lifetime

    The client refreshes every 10 s. Whoever stops refreshing expires.

    SET presence:ada online EX 30
-> OK

  2. The roster, as a set

    SADD online ada
-> (integer) 1
SMEMBERS online
SREM online ada            # on clean disconnect
Cost & limits

Presence by TTL is eventually right: a crashed client shows online for up to the TTL — size the 30 s to how stale you can stand. And SMEMBERS returns the whole set in one reply; on a roster of millions, page through SSCAN instead.

The same thing, between two browser tabs

Two tabs of the same origin: publish in one, render in the other. No server, no WebSocket, no connection state.

  1. Open the engine in each tab

    import { open } from "@goliapkg/kevy";

const db = await open({ persist: { name: "app" } });

  2. Tab A subscribes

    db.subscribe("room:42", (payload, channel) => {
  render(JSON.parse(new TextDecoder().decode(payload)));
});

  3. Tab B publishes — tab A renders it

    db.publish("room:42", JSON.stringify({ user: "ada", text: "hello" }));
Cost & limits

The bridge is a BroadcastChannel, so this reaches tabs of the same origin on the same device — filtering still happens inside the engine, but crossing devices is what the server is for. Try it now: open the playground in two tabs and publish from either one.
