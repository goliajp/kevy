Version 4.0

Your data needs somewhere fast to live.
It is not always a server.

kevy is a Redis-compatible store that runs in more than one place. The same engine serves a 16-core machine, sits inside your binary with no socket at all, ships to a browser tab as 151 KB of WebAssembly, and boots on a microcontroller with no operating system. You learn one API and use it everywhere.

Why this exists

Redis is excellent and most teams should keep using it. kevy was built because a Redis-shaped hole kept appearing in places Redis cannot go.

You cannot put Redis inside a desktop app so it works offline. You cannot ship it to a browser tab. You cannot boot it on a sensor with 256 KB of RAM. Each of those ends with someone writing a fourth storage layer — its own API, its own bugs, its own idea of what a TTL means. kevy is one engine that fits all four, and it speaks the protocol your team already knows.

It has no third-party dependencies: not a hashmap crate, not a hasher, not an async runtime. That is not a flourish — it is the reason the same code compiles for a server, a browser and a microcontroller. Any crate that assumes a heap, a thread or a clock would close one of those doors.

Why teams move to it

Three reasons people actually switch. If none of them is your reason, keep the thing you have — it is working.

Reason one

You need it where Redis cannot go

A CLI that works on a plane. A web app that survives a reload with no backend. A device with no OS. Today those get a separate storage layer each; with kevy they get the same one.

Coming from Redis Reason two

You can delete a service

Secondary indexes, materialised views, vector KNN, BM25 full-text and a change feed are in the engine. No search cluster beside your cache, no modules, no second copy of the data drifting from the first.

See what it can index Reason three

Your database is doing work it hates

Sessions, rate limits, queues, feature flags, hot rows. Those reads are lookups, not questions — and they are the ones hammering your Postgres.

Read the last two rows before you decide. Against Redis 8, LPUSH is ahead by 12% and ZADD by 10% — close enough that your value sizes and key distribution decide the winner, not the engine. If lists or sorted sets are your hot path, speed is not a reason to switch.

What kevy will not do

It is not a cluster. Replication and failover exist; sharding data across machines does not, and will not. If one machine is not enough, kevy is the wrong answer. There is no AUTH and no TLS — run it on a private network or behind something that does those properly. And some commands differ from Redis in ways that will surprise you: SCAN is not a cursor iterator, ZRANK is O(N), SPOP is not random. Every difference is written down, per command, in a column Redis's own reference does not have.
