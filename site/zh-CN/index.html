同一个引擎,四个落点。

kevy 是从零手写的 Rust 存储引擎,不引入任何第三方 crate —— 哈希表、分配策略、 协议解析、事件循环,全部自研。正因如此,同一个引擎既能吃满 16 核服务器,也能塞进 没有操作系统的单片机。先找到你的处境:

架构

thread-per-core,零共享

每个 shard 在自己的核上独占一段键空间,跑自己的 reactor —— Linux 上走 io_uring。热路径上没有跨核锁,也没有会在最糟糕时刻停顿的 GC。

兼容性

客户端一行都不用改

线上跑 RESP2 与 RESP3,CI 里逐字节与 valkey 9.1 做差分测试。Lua(EVAL)、pub/sub、streams、事务、键空间通知都在。

可用性

复制与故障切换是长出来的,不是贴上去的

主从复制带真正的写日志,基于 epoch 围栏的多数派选举,计划内 FAILOVER,read-your-writes 令牌,有界陈旧度,以及静态范围的集群。

CH 02

把存储放进你的程序里

consumer 构建 · opt-level z · fat LTO

没有守护进程、没有 socket、没有序列化:kevy-embedded 是你的程序直接调用的一个 Rust 库。 因为 kevy 不依赖任何东西,所以交叉编译时既没有 C 工具链要装,也没有一堆 -sys crate 要伺候 —— 这正是它能落到别的存储引擎到不了的板子上的原因。下面每一行都是真跑出来的,不是 cargo check 出来的。

裸机

它能在单片机上启动

不是 cargo check:CI 会构建一个真固件 —— 手写向量表、bump 分配器、panic handler、semihosting, 因为一个零依赖的引擎不能去拿 cortex-m-rt —— 然后在 QEMU 的 Cortex-M4 上真的把它启动起来,每次 push 都跑。

  • 固件镜像 145 KB
  • 空库的堆占用 0 字节 —— 你不写它就一个字节都不分配
  • 64 个传感器键 17.8 KB;固件推进自己的时钟后,TTL 正常过期
  • 跑在那里的是存储引擎本身,不是完整的 embedded 外观层 —— 那一层需要 std

CH 03

在浏览器里存真正的数据

headless Chrome · 10 万键 · 16 字节值

它不是 IndexedDB 的一层包装 —— 而是引擎本身编译到 WebAssembly,C ABI 手写,不用 wasm-bindgen。 所有操作都在 wasm 线性内存里跑;写日志在热路径之外成批刷到 OPFS。 用 IndexedDB 存一份日志,和把 IndexedDB 当引擎用,是两回事 —— 下面的条形量的就是这个差别。

点写 · ops/秒 · 10 万键

kevy(wasm)1,787,310
localStorage361,696 4.9×
IndexedDB9,479 189×

扫描也是一样的走向:在 10 万键上做一次模式扫描,kevy 用 5.6 ms, IndexedDB 用 254 ms —— 46 倍。

kevy 输掉的那条轴

读小值,localStorage 更快。而且永远会更快。

getItem 是一次原生的同步哈希查找,不跨任何边界。而 kevy 的每一次读都要编码 key、 跨进 wasm、再把值拷回来 —— 在一个 16 字节的值上,这趟穿越比查找本身还贵。 用 mget() 批量能追回约 1.5 倍,但仍然是输的: 逐 key 编码和逐值拷贝都是线性的,摊不掉。

所以:如果你的数据量小、只有字符串、而且读多写少,就用 localStorage。 kevy 的价值出现在超过 ~5 MB 之后,出现在写、扫描、TTL 上,以及当「同步写阻塞你的标签页」这件事不可接受的时候。

持久化

OPFS主通道

活过刷新,而不是活在一个变量里

写日志追加进源私有文件系统(OPFS);在拿不到同步句柄的环境里回退到 IndexedDB。刷新页面,数据从磁盘回来。

CH 04

给 agent 一个能检索的记忆层

kevy-mcp · stdio · 零依赖 JSON-RPC

会话状态、情节记忆、RAG 语料,通常意味着三套系统。在这里它们是一个库: 向量 ANN、全文 BM25、二级索引,建在同一个键空间上,并且有把它们融合起来的混合召回 —— 再加一个 MCP server,让 agent 直接够到它,而不是穿过一层要你自己维护的胶水。

召回

四种索引,一个键空间

  • 向量 ANN(HNSW)—— 基于你提供的 embedding 做语义召回
  • 全文 —— 倒排分段,BM25 排序
  • 范围 / 唯一 —— 普通的二级索引
  • 混合 —— 向量 × 全文的 RRF 融合,在服务端归并

触达

agent 直接跟它说话

kevy-mcp 是一个走 stdio 的 MCP server,同样遵守零依赖规矩 —— 它的 JSON-RPC 是手写的。

刻意做成五个工具,而不是五十个:discover(让 agent 自己去读命令表)、read、explain、info,以及 write —— 写要显式开启。命令以 argv 数组传入,所以不必「一个动词一个工具」就能够到整个命令面。

它们的 schema 与 COMMAND DOCS、llms.txt 出自同一张命令表 —— 单一事实源,在 CI 里对账防漂移。

形态

TTL 就是记忆策略

会话上下文自己过期。情节记忆同时挂向量索引和时间索引。chunk 就存在它对应的向量旁边,所以召回直接把正文给你,而不是给你一个还得再去取一次的 row id。
