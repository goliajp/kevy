实时

推给所有
正在听的人

聊天、在线状态、通知、一个会自己更新的仪表盘。一次发布，多个订阅者，不用轮询。而在浏览器版本里，同一套发布订阅在两个标签页之间也能用，完全不需要服务端。

为什么合适——以及哪里不合适

发布订阅是发完就不管的。一条消息只会送给那一刻正在订阅的人；晚一秒才连上来的人永远看不到它，而且没有确认。对于一次在线心跳、一个实时计数器，这正好合适；对于任何你丢了会心疼的东西，这正好不合适。

如果丢一条消息是要紧的，就改用 stream——见队列。stream 保留历史，支持消费组，还能让掉过线的客户端把落下的补回来。发布订阅是便宜的那一个；便宜本身就是这笔交易的内容。

把一条消息扇出给所有正在听的人

一次发布，送达那一刻在线的每一个订阅者——一个聊天室、一条通知、一个实时计数器。

  1. 每个客户端各自订阅

    PSUBSCRIBE 用一条连接就能订下一整族频道。

    SUBSCRIBE room:42
PSUBSCRIBE room:*          # every room, one connection

  2. 发布——返回值就是听众数

    PUBLISH room:42 '{"user":"ada","text":"hello"}'
-> (integer) 3             # how many subscribers received it
成本与限制

跟不上的订阅者会被丢掉，而不是被无限缓冲。如果一个客户端跟不上，它的消息会被丢弃，而不是让服务端的内存无上限地涨下去——这是有意的选择，在你依赖投递之前应该先知道它。没有确认，也没有重放：只要这两样里有一样要紧，你要的就是 stream，不是频道。发布订阅指南把边界写得很具体。

在线状态——现在谁在线

记账的活交给引擎的过期机制：一个安静下来的客户端，会自己从名单上掉下去。

  1. 心跳：一个带寿命的 key

    客户端每 10 秒续一次。谁停止续期，谁就过期。

    SET presence:ada online EX 30
-> OK

  2. 名单，用一个 set

    SADD online ada
-> (integer) 1
SMEMBERS online
SREM online ada            # on clean disconnect
成本与限制

靠 TTL 的在线状态是最终正确的：一个崩掉的客户端最长会显示在线一个 TTL——这个 30 秒要按你能忍多陈旧来定。另外 SMEMBERS 会把整个 set 一次性返回，名单到了百万级，改用 SSCAN 分页。

同一件事，在两个浏览器标签页之间

同源的两个标签页：在一个里发布，在另一个里渲染。没有服务端，没有 WebSocket，也没有连接状态。

  1. 在每个标签页里打开引擎

    import { open } from "@goliajp/kevy";

const db = await open({ persist: { name: "app" } });

  2. 标签页 A 订阅

    db.subscribe("room:42", (payload, channel) => {
  render(JSON.parse(new TextDecoder().decode(payload)));
});

  3. 标签页 B 发布——A 把它渲染出来

    db.publish("room:42", JSON.stringify({ user: "ada", text: "hello" }));
成本与限制

桥是一个 BroadcastChannel，所以它到达的是同一台设备上同源的标签页——过滤仍然发生在引擎内部，但要跨设备，那就是服务端的活了。现在就可以试：在两个标签页里打开 playground，从任意一边发布。
