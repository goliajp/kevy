队列与任务

把活交给 worker，
worker 挂了还能把活拿回来

关系型数据库里的队列表，本质是一套加了额外步骤的加锁约定。kevy 有两种真正的队列：丢一个任务还能承受的时候，用 list；承受不了的时候，用带消费组的 stream。

两种选哪种

用 list：任务重做一遍成本很低，worker 也不太可能干到一半挂掉——发一封邮件、预热一个缓存、让一条 CDN 路径失效。BRPOP 会一直阻塞到有活为止，所以 worker 不必轮询。

用 stream：任务绝对不能丢。消费组会把每条消息恰好交给一个 worker，并且记住自己交过。如果这个 worker 在确认之前挂了，消息会留在 pending 列表里，另一个 worker 可以把它认领走——stream 存在的全部理由就是这个，它也正是一个队列和一份侥幸之间的差别。

list，给可以重来的活

生产者往里推，阻塞着的 worker 在有活的那一刻醒来。两条命令，没有轮询循环，也没有调度器。

  1. 生产者：把任务推进去

    LPUSH jobs:email '{"to":"ada@example.com","tpl":"welcome"}'
-> (integer) 1

  2. worker：阻塞到有活为止

    没有轮询循环，没有 sleep，也没有惊群——任务一到，pop 立刻返回，等满 30 秒还没有就空手返回。

    BRPOP jobs:email 30
-> 1) "jobs:email"
   2) "{\"to\":\"ada@example.com\",\"tpl\":\"welcome\"}"

  3. 延时任务：score 就是到期时间

    ZPOPMIN.BELOW 是 kevy 自己的命令——它只取真正到期的，遇到第一个没到期的就停下。

    ZADD jobs:due 1783875499 '{"id":"j-91"}'
-> (integer) 1
ZPOPMIN.BELOW jobs:due 1783875500
-> the job payload, only if it is due
成本与限制

被 pop 走却没被 worker 干完的任务，就没了。这是整件事只要两条命令的代价——只把可以重来的活交给它。另外在多分片的服务端上，BLPOP 跨多个 key 时并不遵守 Redis 那种严格的从左到右优先级：连接自己所在分片上的 key 会先被服务。

stream，给丢不起的活

每个任务恰好交给一个 worker，在被确认之前一直是 pending。挂掉的 worker 手上的任务可以被认领走，全部历史都还在。

  1. 初始化时做一次：建消费组

    XGROUP CREATE jobs:pay g1 $ MKSTREAM
-> OK

  2. 生产者：把任务追加进去

    XADD jobs:pay * order 4410 amount 8400
-> "1783875499458-0"

  3. worker：先读，再干活，然后确认

    你确认的 ID 就是 XREADGROUP 交到你手上的那个。在 XACK 之前，这个任务一直是 pending——记在你名下，记在账上。

    XREADGROUP GROUP g1 worker-3 COUNT 1 BLOCK 5000 STREAMS jobs:pay >
XACK jobs:pay g1 1783875499458-0

  4. worker 在 XACK 之前挂了：把它的任务认领回来

    XAUTOCLAIM jobs:pay g1 worker-7 60000 0-0
# claims anything idle for more than 60 s

XPENDING jobs:pay g1
# what is still outstanding, and who has it
成本与限制

stream 不是免费的。用 MAXLEN 裁剪会重算整条流的权重，复杂度是整条流的 O(N)——按计划裁剪，不要每次 XADD 都裁。XREADGROUP 的 COUNT 限制的是交到你手上的条数，不是扫过的条数：整条尚未投递的尾巴会先被物化出来。逐条命令的细节在命令参考里。
