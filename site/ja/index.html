ひとつのエンジンが、四つの場所で動く。

kevy は Rust でゼロから書いたストレージエンジンです。サードパーティのクレートを一切使っていません —— ハッシュマップも、アロケーション戦略も、プロトコルパーサも、イベントループも、すべて自前。 だからこそ同じエンジンが 16 コアのサーバーにも、OS すら載っていないマイコンにも収まります。 まず、ご自身の状況を選んでください:

CH 01

本番の Redis を置き換える

-c 50 -P 16 · n=800万 · 5 回の中央値 · 同一マシン

同じハードウェア、同じ計測手順。サーバーはコア 0–7、負荷生成側は 8–15 にピン留めしています。 これはパイプライン負荷でのスループット上限 —— つまり、実負荷下のキャッシュの姿です。 このページの数字はすべて実測であり、負けている項目もそのまま載せています。

位置づけ · パイプラインスループット上限

kevy は 639万 GET/s、 638万 SET/s。バーは kevy を基準にした相対値、 右端の数字は kevy が何倍速いかを示します。

kevy 4.0 639万 GET/s
redis 8 1.60×
valkey 9.1 3.00×
dragonfly 3.60×

興味深いのは dragonfly です。同じ shared-nothing 系であり、しかも 私たちが検討したうえで採用しなかった手法をすべて使っています —— io_uring BUNDLE、MSG_RING、direct descriptor —— それでも 1 操作あたり 10,400 サイクル、私たちの 2.2 倍を費やします。redis 8 は単一スレッド実行(コア使用率 43%)、 valkey 9.1 は サイクルの 33% を io-thread 間の pthread_mutex_lock に使っています。

アーキテクチャ

thread-per-core、共有なし

各シャードが自分のコアでキースペースとリアクタを専有します(Linux では io_uring)。ホットパスにコア間ロックはなく、最悪のタイミングで止まる GC もありません。

互換性

クライアントは変更不要

ワイヤは RESP2 / RESP3。CI で valkey 9.1 とバイト単位の差分テストを行っています。Lua(EVAL)、pub/sub、streams、トランザクション、キースペース通知に対応。

可用性

後付けではないレプリケーションとフェイルオーバー

本物の書き込みログを持つプライマリ／レプリカ、エポックによるフェンシング付きの多数決選出、計画フェイルオーバー(FAILOVER)、read-your-writes トークン、有界の陳腐化、静的スコープのクラスタ。

CH 02

ストアをプログラムの中に置く

consumer ビルド · opt-level z · fat LTO

デーモンもソケットもシリアライズもありません。kevy-embedded は、あなたのプログラムが直接呼ぶ Rust ライブラリです。 kevy は何にも依存していないので、クロスコンパイルに C ツールチェーンも -sys クレート群も要りません —— だからこそ、ほかのストアが届かないボードにまで届きます。下の各行は cargo check ではなく、実際に動かした結果です。

ベアメタル

マイコン上で起動します

cargo check ではありません。CI は本物のファームウェアをビルドし —— ベクタテーブル、バンプアロケータ、 パニックハンドラ、セミホスティングまで手書きです。依存ゼロのエンジンが cortex-m-rt に頼るわけにはいかないので —— それを QEMU 上の Cortex-M4 で実際に起動させます。push のたびに。

  • ファームウェアイメージ 145 KB
  • 空ストアのヒープ使用量 0 バイト —— 書くまで 1 バイトも確保しません
  • センサキー 64 件で 17.8 KB。ファームウェアが自前の時計を進めれば TTL は正しく失効します
  • そこで動くのはストレージエンジン本体であって、組み込み用ファサード層ではありません —— そちらは std を必要とします

CH 03

ブラウザに本物のデータを置く

ヘッドレス Chrome · 10万キー · 16 バイト値

IndexedDB のラッパーではありません —— エンジンそのものを WebAssembly にコンパイルしたもので、 C ABI は手書き、wasm-bindgen は使いません。すべての操作は wasm のリニアメモリ上で走り、 書き込みログはホットパスの外でまとめて OPFS に流します。 IndexedDB にログを置くことと、IndexedDB をエンジンとして使うことは別物です —— 下のバーが測っているのは、まさにその差です。

点書き · ops/秒 · 10万キー

kevy(wasm)1,742,160
localStorage365,464 4.8×
IndexedDB9,168 190×

スキャンも同じ傾向です。10万キーに対するパターンスキャンは kevy が 5.5 ms、 IndexedDB が 257 ms —— 47 倍。

kevy が負ける軸

小さな値の読み出しは localStorage のほうが速い。これは今後も変わりません。

getItem はネイティブの同期ハッシュ探索で、境界を一切またぎません。一方 kevy の読み出しは毎回、 キーをエンコードし、wasm 境界を越え、値をコピーして返します —— 16 バイトの値では、その往復のほうが探索本体より高くつきます。 mget() でまとめれば約 1.5 倍取り戻せますが、それでも負けます。 キーごとのエンコードと値ごとのコピーは線形で、償却できないからです。

つまり、データが小さく、文字列だけで、読み取り中心なら localStorage を使ってください。 kevy が効いてくるのは 5 MB を超えたあたりから、そして書き込み・スキャン・TTL、 さらに「同期書き込みでタブが固まる」ことが許容できない場面です。

永続化

OPFS主経路

変数の中ではなく、リロードを越えて生き残る

書き込みログは OPFS(オリジン専用ファイルシステム)に追記します。同期ハンドルが使えない環境では IndexedDB にフォールバック。タブをリロードすれば、データはディスクから戻ります。

タブ間

0.1ms p50

タブ間の pub/sub

BroadcastChannel 上に載せた本物のチャネル購読・パターン購読です。粗い storage イベントではありません。一方のタブで publish すれば、他方がミリ秒未満で受け取ります。

CH 04

エージェントに検索できる記憶を与える

kevy-mcp · stdio · 依存ゼロの JSON-RPC

セッション状態、エピソード記憶、RAG コーパス —— 普通なら三つのシステムになります。ここではひとつのストアです。 ベクトル ANN、全文 BM25、セカンダリインデックスが同じキースペースの上に載り、それらを融合するハイブリッド検索があります。 さらに MCP サーバーが付くので、エージェントは自作の接着コードを経由せず直接触れます。

検索

四種類の索引、ひとつのキースペース

  • ベクトル ANN(HNSW)—— あなたが用意した埋め込みによる意味検索
  • 全文 —— 転置セグメント、BM25 でランキング
  • 範囲 / ユニーク —— 通常のセカンダリインデックス
  • ハイブリッド —— ベクトル × 全文の RRF 融合をサーバー側でマージ

到達

エージェントが直接話しかける

kevy-mcp は stdio 上の MCP サーバーで、同じ依存ゼロの規律で書かれています —— JSON-RPC も手書きです。

あえてツールは 5 個、50 個ではありません:discover(エージェント自身がコマンド表を読む)、read、explain、info、そして write —— 書き込みは明示的に有効化します。コマンドは argv 配列で渡すので、動詞ごとにツールを生やさなくても全機能に届きます。

これらのスキーマは COMMAND DOCS や llms.txt と同一のコマンド表から生成されます —— 単一の正となる情報源で、CI が乖離を検出します。

形

TTL がそのまま記憶ポリシー

セッションコンテキストは自分で失効します。エピソード記憶はベクトルと時刻の両方の索引を持ちます。チャンクは元になったベクトルの隣に置くので、検索結果は本文そのものを返します —— あとで引き直す必要のある row id ではなく。
