kevy in a Tauri app

A Tauri app's backend is Rust — so kevy embeds directly, no server and no separate process. tauri-plugin-kevy holds one kevy-embedded Store in Tauri's managed state and exposes it to the webview over invoke. One shared store, reachable from every window and from your Rust code alike.

Full guide, install steps, and the API table: bindings/tauri/README.md.

The shape

The webview reaches the whole engine: typed get/set/del/incr, pub/sub streamed over a Tauri Channel, and a raw cmd(argv) path for every other verb (HSET, ZADD, IDX.*, …) — the same client contract the language clients implement.

Two doors: backend store vs. wasm

kevy can also run entirely in the webview as WASM. Choose by where the data lives:

  • Backend store (this plugin) — one native store shared across windows and Rust, durable (snapshot + AOF), one IPC hop per call. The app's real data.
  • wasm in the webview — an isolated, ephemeral store scoped to a single webview, no IPC. Sandboxed scratch space.

The binding README has the full decision table.

The 0-dep boundary

kevy's workspace is strictly 0-dependency. A Tauri plugin must depend on the tauri crate, so tauri-plugin-kevy sits outside the workspace (root Cargo.toml exclude), depending on tauri + the 0-dep kevy-embedded and kevy-resp. cargo build at the repo root never sees tauri; the engine stays pure.
