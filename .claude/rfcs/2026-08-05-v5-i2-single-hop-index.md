# I2:索引即键、单跳 —— 设计轮(现状对照 + 拍板题)

> 总案 §R3 收尾时留下的唯一开放方向。R3 Phase A/B 已经把
> `IDX.QUERY` 的成本拆到段级并打完三轮攻击(A3 落地、A1/A2 证伪),
> 结论是:**查询路径本身不慢,剩下的全是扇出宽度本身**。
> 扇出是路由模型的产物,不是代码的产物,所以下一步是设计轮不是攻击轮。
> 本文只陈述与建议;**拍板权归属主,批准前零实现代码**(v5 arc 铁律)。

## 〇、I2 的原文与现状

总案 `2026-07-26-v5-arc-design-input.md:43`:

| I2 | 一切按 key 路由到属主 | 一请求一跳。**目前 `IDX.QUERY` 是唯一的例外** |

这条"例外"在代码里是一行:`crates/kevy/src/cmd_resolve.rs:184`
`b"IDX.QUERY" => Route::Extension` —— `Route::Extension`
(`kevy-rt/src/route.rs:72-74`)= 每个 shard 都跑一遍、origin 归并。
IDX.EXPLAIN / COUNT / VERIFY / LIST、VIEW.\*、TABLE.LIST/VERIFY
同族(`cmd_resolve.rs:185-197`)。

模型上这是**分区局部二级索引**(local / partitioned secondary index):
索引与它所索引的行同分片,写是纯本地的,读必须扇出到所有分片再归并。
它的对偶是**全局二级索引**(global secondary index):索引按**被索引值**
分区,读单跳,写要跨分片。I2 说的"索引即键"就是后者。

## 一、R3 量到的:扇出到底值多少

**这一节的每个数都是实测,不是估算。** 出处:
`bench/PERF-DECOMP-2026-08-04-idx-page-vs-pg18.md` +
`bench/PERF-FINDING-2026-08-05-r3-a3-reduce-borrow.md` +
`bench/PERF-FINDING-2026-08-05-r3-a5-syscall-face.md`。

**(a) 宽度扫描**(同一数据集内部可比,与下面 2M 行的绝对值不可混):

| shards | idx p50/p99 | page p50/p99 |
|---|---|---|
| 1 | **36/54** | **43/67** |
| 4 | 58/72 | 71/111 |
| 8 | 63/80 | 100/111 |
| 16 | 104/371 | 156/201 |

单分片路径比 PG18 同形快约 3×;**p50 从 36 走到 104 全是宽度税**。

**(b) 一次扇出查询在 reactor 上的账**(width 14,2M 行,每查询):

* 26 个唤醒目标 / 8–13 次真 pipe write(peer 处于 park 才写)
* 14 次 wake flush、8–13 次 park 进入
* reduce 归并的 union = min(width × LIMIT, 命中行数) —— page 形 ~250 条

**(c) 已经攻掉的和攻不动的**:A3(借用排名)把 page p50 从 150 打到
119 = 与 PG18 打平;A1(nap)与 A2(唤醒批量化)双双证伪;syscall 面
被证明是税不是瓶颈(数动 140×,p50 不动)。**攻击面已经空了。**

**(d) 写侧的余量**(这条决定 GSI 是否可谈):

| | kevy write p50/p99 | PG18 write p50/p99 |
|---|---|---|
| gate 1 三轮 | 29/40 · 29/42 · 29/40 µs | 727/1457 · 819/1646 · 746/1587 µs |

**kevy 的写比 PG 快 25×**。给带索引的写加一跳跨分片(经验量级
10–20 µs)之后仍然快一个数量级 —— 这是"读单跳"这条路在**本项目**
可谈的唯一理由,换个写侧没余量的引擎就不成立。

## 二、设计空间(四条,含"不做")

### 方案 A —— 全局二级索引(索引按被索引值分区)

`shard_of(index_name, value)` 决定条目落哪个分片。读:origin 算出
目标分片 → 单跳 → 该分片本地跑完整个 `range` + LIMIT → 回。
写:行属主分片写完行,再向索引属主分片发一条索引 delta。

* **读**:`Route::Extension` → `Route::Single`,union 归并整个消失
  (A3 攻的那段代码在这条路上不存在),13 次唤醒写、13 次 park、
  13 份 chunk 编解码全消失。上限 = 宽度扫描的 width-1 那一列。
* **写**:本地 + 1 跳。写放大 = 每个被更新的索引一跳(一行常有 2–3 个索引)。
* **覆盖问题(关键)**:`FIELDS` 要回行读。kevy **已经有覆盖索引**
  (`IDX.CREATE … VALUES f…`,`cmd_index.rs:51`;存储在
  `kevy-index/src/rowvalues.rs:74` `RowValues`)—— 覆盖索引下整个
  查询在索引分片一跳答完;不覆盖的字段要么退化成二次扇出,要么
  **拒绝**(把"未覆盖字段"做成 IDX.ADVISE 的一条建议,与 R4b 的
  自动声明闭环同形)。
* **一致性**:行写与索引写不再原子。kevy 没有分布式事务,现有的
  跨分片写路径是消息传递。可选契约:读己写(同 conn 顺序保证)、
  最终一致 + `IDX.VERIFY` 兜底(已存在)、或索引写同步等 ack(把
  写变成 2 跳往返 ≈ +30–60 µs,仍远快于 PG)。**这是本方案最大的
  拍板题,不是实现细节。**

### 方案 B —— 整个索引落单分片(按索引名分区)

`shard_of(index_name)`。读单跳,写单跳,实现比 A 简单得多
(不需要按值路由,不需要 range 跨分片切分)。
代价:一个索引的全部条目和全部查询压在一个核上 —— SME 4–8 核、
单表几千万行的场景下,这个核成为该索引的吞吐上限。
**适合小基数索引,不适合主力索引。**

### 方案 C —— 保持局部索引,只收窄扇出宽度

不改模型,只让 `IDX.QUERY` 打到分片的一个子集(与 v1.30
`--accept-shards` 同族思路)。问题:局部索引下任何一个分片都可能
持有答案,少打一个分片就是漏结果 —— **除非行本身按索引值共置**,
而那就回到了方案 A 的分区问题。所以 C 只在"行的分区键恰好是索引列"
时成立,是 A 的一个特例,不是独立方案。

### 方案 D —— 不做,只给部署指导

R3 已经给出的两条:`--threads ≤ cores − 2`(消 p99 悬崖)、
SME 4–8 核上 kevy 两轴本来就赢 PG。代价:16 核以上的箱子上
`IDX.QUERY` 的 p50 永远带宽度税;总案 I2 那条"唯一的例外"永远留着。

## 三、判据(建议写成结构性陈述,不是"比 PG 快 X%")

若拍板走 A,建议的验收线(v5 铁律①:**验收线 = 结构性陈述**):

1. **跳数陈述**:一次覆盖索引查询的跳数 = 1(origin ≠ 索引属主时)
   或 0(恰好本地),与分片数无关 —— 可由 R3 A5 的探针
   (`INFO reactor`)直接证伪:`wake_targets/query` 应从 26 掉到 ≤ 2。
2. **成本组成陈述**:查询成本 = 解析 + 一次树 walk + 一次编码,
   **不含**归并项 —— union 规模从 min(width×LIMIT, matches) 变成
   matches∩LIMIT,A3 攻的那一段成本项从账上消失。
3. **写侧陈述**:带索引的写 = 本地行写 + 每个受影响索引一条跨分片
   消息;写放大与索引数线性,与分片数无关。
4. **一致性陈述**:写与索引可见之间的窗口有明确上界,且
   `IDX.VERIFY` 能把不一致检出(不是"应该不会不一致")。

## 三b、与 ROADMAP T7 已锁定前提的对账(**这段修正本文前面的口径**)

写完上面几节后核对 `.claude/ROADMAP.md` 的 **T7 —— 索引即键(消 I2
特例)**,发现本文的论证口径与那里**已经写死的诚实前提**不一致,
必须当面改口而不是留着:

> **诚实前提**:按 SME 的 4-8 核重读,索引查询 kevy 本来就赢
> 1.9-2.8×(扇出是 16 核放大的问题)⇒ **本 train 的理由是模型内在
> 一致性,不是补性能短板**。

**R3 的实测站在 ROADMAP 这一边,不站在"性能短板"那一边**:宽度扫描
里 4-8 shard 的 idx p99 是 72-80µs vs PG 的 164,page 111 vs 147 ——
**SME 的家门口 kevy 两轴本来就赢**;宽度税只在 16 shard 那一档显形,
而那一档的 p99 悬崖已被证明是**部署形状**(`--threads ≤ cores − 2`,
14 shard 时 idx p99 98µs 已胜 PG 164)。A3 落地后 page p50 也已与
PG18 打平。

所以本文 §一 那些数**是对的,但不是买 A 的理由**。正确的口径:

* **不选 A,SME 部署不损失什么** —— 这是 D 的真实成本,比本文 §二
  D 段写的"永远带宽度税"要轻。
* **选 A 的理由是模型**:I2 说"一切按 key 路由到属主,一请求一跳",
  `IDX.QUERY` 是唯一的例外;消例外让**路由规则只有一条**,而不是
  一条加一个特例。ROADMAP 用的词是"消特例而非加特例"。
* **性能是副产物,不是论据**。16 核以上的箱子会得益,但那不是
  SME 的形状,而 SME 是本 arc 的目标人群(愿景拍板:企业规模不是
  数据规模)。

**这条对账改变了 Q1 的问法**:不是"值不值得为性能买这一跳",而是
"**为了模型只有一条路由规则,愿不愿意付跨分片写维护的复杂度**"。

## 四、拍板题(四个,属主定)

**Q1 — 走哪条?** A(全局索引,读单跳/写一跳)/ B(索引落单分片)/
D(不做,只留部署指导)。**按 §三b 的对账,这题是模型题不是性能题**:
A 的收益是路由规则从"一条 + 一个特例"变成"一条";D 的代价在 SME
形状上接近于零(4-8 核两轴本来就赢),只在 16 核以上的箱子留宽度税。
写侧 25× 的余量说明**这一跳付得起**,但付不付得起 ≠ 该不该付 ——
后者是模型口味,归属主。

**Q2 — 一致性契约取哪档?** (i) 异步 + IDX.VERIFY 兜底(写最快,
读可能看不到刚写的)/ (ii) 同 conn 读己写(需要在 origin 记 pending
索引写,读时等)/ (iii) 索引写同步 ack(写 +30–60 µs,语义最简单)。
建议 **(iii) 起步**,而且这不只是口味问题:总案把
**I3 = derived-by-construction(写路径同步维护、永不漂移)**
列为**固有性质**并明说"这正是 S3(没有 DBA)的技术实现"
(`2026-07-26-v5-arc-design-input.md:44`)。(i) 直接把 I3 从
"同步维护"降级成"最终一致 + 校验工具",**那是在动一条已锁定的
固有性质,不该作为 I2 的副作用悄悄发生** —— 要动就单独拍。
(iii) 保住 I3;而且松紧方向只能由紧到松,反向会打破已发出去的
消费者预期。

**Q3 — 未覆盖字段怎么办?** (i) 二次扇出回行读(语义全,性能塌回去)/
(ii) 具名拒绝 + IDX.ADVISE 建议把字段加进 `VALUES`(与 R4b
自动声明同形,语义面一致)。建议 **(ii)**。

**Q4 — 迁移面。** 现有索引是局部的,切成全局要么重建(`IDX.REBUILD`
已存在,但要跨分片重分布),要么两种索引形态并存(catalog 里加一个
`partitioning: local | global` 字段,新建默认哪个?)。建议
**并存 + 新建默认 local**,全局是显式声明 —— 与"KV/pubsub 不得退化"
同一条谨慎线。

## 五、建议切片(若 Q1 拍 A)

> 每片一条 feature 分支,片间可停。

* **I2-s1 —— 路由与 catalog**:`partitioning` 字段进 TableSpec/IdxSpec
  与 sidecar(第九字段);`shard_of(index, value)` 的编码定死
  (复合索引按首列?按整键?—— 这一条本身要在 s1 的设计里钉死,
  因为它决定 range 查询能否单跳:**按值 hash 的话 range 查询就不能
  单跳了**,必须按值**序**分区,即索引自身范围分片)。
* **I2-s2 —— 写侧**:行写后的索引 delta 消息(新 `Inbound` 变体)、
  Q2 拍板的一致性契约、崩溃语义(crashgate 加 cell)。
  **起点必须是"哪些路径会改一个 key"的完整清单** ——
  写这份 RFC 时顺手追出两个真 bug(多键 DEL/UNLINK/RENAME 留陈旧
  索引条目;MOVE-SCOPE 迁入的行永不进索引,且 `IDX.VERIFY` 看不见
  这个方向),根因就是"写路径同步维护"里的"写路径"实际只指其中
  一条。局部索引下漏一条路径 = 一处漂移;**全局索引下漏一条路径 =
  一条跨分片消息没发,后果同样是静默错答**。清单见
  `bench/FINDING-2026-08-05-index-drift-on-non-dispatch-writes.md`
  (已修,分支 `fix/idx-drift-on-multikey-writes`)。
* **I2-s3 —— 读侧**:`Route::Extension` → 按值算目标分片的新 Route;
  覆盖判定 + Q3 的拒绝面;A5 探针验证跳数陈述。
* **I2-s4 —— 迁移**:`IDX.REBUILD` 的跨分片重分布;两形态并存的
  IDX.LIST 显示;perfgate/门禁补线。

**s1 的范围分片问题是整条路的真难点**,必须在 s1 的设计轮里解决,
不能带着走 —— 按 hash 分区的全局索引只能答等值查询,而体检单上
输给 PG 的两条(idx = 等值、page = 范围)里有一条正是范围。

## 六、显式不做

* **A6(parse-once fan-out)**:攻击表里最后一条未攻的行,预估
  −1..−2 µs。R3 三轮已经证明 per-op µs 级不动吞吐;若走 A,扇出
  本身消失,A6 连存在的理由都没了。**关闭,不再列为候选。**
* **A2 复活**:除非有人拿出"13 次串行唤醒写延后了最后一个 peer 的
  起跑"的延迟实测,否则不再讨论(A5 已证它不是 syscall 面的攻击)。
* **改 idle 阶梯默认值**:sweep 已证 p50/p99 是对冲,默认不动
  (旋钮留作部署侧兜底)。
