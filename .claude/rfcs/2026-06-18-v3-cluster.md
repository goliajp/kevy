# RFC: v3 cluster — single-primary, replicated reads, embed-as-member, scoped multi-writer, async client

- Date: 2026-06-18
- Status: locked (user-approved design forks 2026-06-18; F1=a, F2=a, F3=b, F4=a, F5=a; open questions Q1=a, Q2=b, Q3=deferred-user-coord, Q4=a+b)
- Scope guard amendment: this RFC **amends** `.claude/scope-decisions.md`'s
  "Cluster mode (multi-machine distributed) = permanently OUT" entry to
  **"single-primary + replicated reads with quorum failover IN; sharded
  multi-master + cross-DC active-active still OUT"**. See § Scope amendment.

## Problem

kevy today is a single-machine, multi-shard, busy-poll engine. v1.17
runs at ~30.8 M GET ops/s on a 16-core box and pub/sub at ~17 M msg/s,
both single-process. Two pressures appeared after the mailrs dogfood
close-out:

1. **Read scaling beyond one box.** kevy already saturates a 16-core
   box on hot keyspaces. Going further means either a 32+-core box
   (linearly diminishing) or distributing reads across machines.
2. **embed ↔ server hot/cold tier with shared state.** mailrs uses
   embed for in-process latency and would like a server tier to absorb
   bursts + cross-process visibility, **but with one shared keyspace**,
   not two independent stores. Today embed and server are
   schema-compatible but state-isolated.

A 3rd pressure (lower urgency, but planned):

3. **async-friendly client.** kevy-client is blocking; tokio/smol users
   wrap with `spawn_blocking`. A native async surface unlocks reactor
   integration on the user side.

## Scope amendment

`.claude/scope-decisions.md` currently lists, under "v∞ permanently
OUT":

> Cluster mode (multi-machine distributed; 2026-06-10 user 澄清:单机
> CLUSTER 协议兼容子集作为 shard 路由载体属 IN,已完成,见「最近完成」③)、
> Replication (primary→replica,单机内部)…

This RFC narrows that entry. New wording (to be applied in scope-decisions.md):

> **Multi-machine cluster** — single-primary + multi-replica with
> quorum-based failover, scoped multi-writer for embed members, and a
> read/write-split client = **IN** (v3 series). **Sharded multi-master**
> (write fans across multiple primaries for the *same* scope) and
> **cross-DC active-active with CRDTs** stay permanently OUT.
> Replication is implemented as `kevy-replicate`.

The single-machine CLUSTER protocol subset (slot routing on one box)
stays as-is; the v3 cluster builds **above** it, not in place of it.

## Design forks — locked

User-approved 2026-06-18.

### F1 = a · scope granularity = key prefix

`[[cluster.scope]]` config blocks declare `prefix = "app:billing:"` (or
similar). A scope is owned by exactly one writer (server primary or
embed member). Writes to keys under that prefix from any other node
return `-MISDIRECTED writer is <node-id>`; reads to any key from any
node are permitted (replicated view).

A node with no scope declaration is **read-only** (a pure replica).

The default config — one global scope `prefix = ""` owned by the
primary server — collapses to plain primary/replica replication, no
multi-writer concept. Phase 1 ships only this default.

### F2 = a · consistency = eventual + `READCONSISTENT` hint

Reads default to whatever replica the client is connected to (may be
stale). Clients that need fresh data add a per-command flag:

```text
GET foo READCONSISTENT
```

`READCONSISTENT` re-routes that read to the scope's owning writer (the
primary for the scope). Default = no flag = `OFF` (eventual). The flag
is a kevy extension; clients without the flag get current Redis-cluster
semantics. v3.1 may add per-connection `READMODE CONSISTENT` to avoid
per-command opt-in.

### F3 = b · failover = automatic via quorum

A new stone-layer crate `kevy-elect` implements failover:

- Each node periodically pings its known peers (config-declared
  topology; no gossip).
- A node is considered DOWN if `quorum_size = (N/2) + 1` peers all
  agree they cannot reach it for `down_after_ms` (default 10 s).
- On primary DOWN, replicas exchange `OFFER-LEADER` messages; the
  replica with the highest replication offset wins; tie-break = lowest
  node-id.
- New primary promotes itself, announces, others reconfigure to
  replicate from it.
- Old primary on rejoin demotes to replica, sync-resets if its offset
  ≤ new primary's, else manual operator intervention required (logged).

This adds split-brain test matrix; failure-injection tests are part of
v3-1.5 (see Phase rollout).

### F4 = a · embed-as-writer crash = server-backed fallback

A scope's `[[cluster.scope]]` block may declare both `writer = embed-A`
and `fallback = server-1`. If the elect protocol declares embed-A
DOWN, server-1 starts accepting writes for that scope. embed-A on
rejoin re-syncs from server-1 and may reclaim writer-ship (manual op
in v3, automatic in v3.1).

If no fallback is declared, the scope is read-only until embed-A
returns (degraded UX; only acceptable for non-critical scopes — config
linter warns).

### F5 = a · async = runtime-agnostic core + feature-gated runtimes

A new `kevy-client-async` crate exposes the same surface as
`kevy-client` but with futures:

```rust
#[cfg(feature = "tokio")]
let mut conn = AsyncConnection::open("kevy://host:6004").await?;
let v = conn.get(b"k").await?;
```

The core crate is `no_std`-clean and only depends on `core::future`.
Concrete runtimes (`tokio`, `smol`, `async-std`) ship as Cargo
features that wire up TcpStream → AsyncRead/AsyncWrite. **The
non-async `kevy-client` stays the default and remains 0-dep**;
async is opt-in for users who already have a runtime.

> **⚠️ EXEMPTION from the 0-dep / pure-Rust rule** (user-confirmed
> 2026-06-18). `kevy-client-async` is the **only** crate in the
> workspace permitted to depend on crates.io third parties — namely
> `tokio`, `smol`, `async-std` behind feature gates, each with
> `default-features = false` and only the minimum-surface features
> needed. The exemption is narrow: it does not extend to any other
> crate, any tokio-utility (`tokio-util`, `tokio-stream`, etc.), or
> any new runtime adapter. Every dep line must carry an inline
> `# EXEMPTION — see feedback-pure-rust-no-c-principle.md` comment
> so audit grep stays one command. No other kevy crate may take
> `kevy-client-async` as a dependency (no transitive bleed). The
> rationale, scope, and audit method are recorded in memory
> `feedback-pure-rust-no-c-principle.md`.

## Architecture

```
                              GLOBAL READ VIEW
                              (any node reads everything)
                                     ↑
        ┌────────────┬───────────────┼───────────────┬────────────┐
        ↓            ↓               ↓               ↓            ↓
   ┌────────┐   ┌────────┐      ┌────────┐      ┌────────┐   ┌────────┐
   │Primary │   │Replica │      │ embed  │      │ embed  │   │ server │
   │ server │   │ server │      │ scope=A│      │ scope=B│   │ relay  │
   │ writes │   │  read  │      │A writes│      │B writes│   │ assist │
   └────────┘   └────────┘      │ all rd │      │ all rd │   │ no wrt │
        │            │           └────────┘      └────────┘   └────────┘
        ↓            ↑                ↓               ↓            ↑
        └────────────┴───── AOF stream / event bus ──┴────────────┘
                  ↑ every node subscribes to other writers' streams,
                    applies inbound writes to its local store
```

The mechanism is shared across all 4 phases: an **AOF stream protocol**
that any node can publish to or subscribe to. What changes per phase is
**who runs the protocol**:

- Phase 1: only the server primary writes; only replicas subscribe.
- Phase 2: embed nodes can also subscribe (become read-replicas).
- Phase 3: embed nodes can also write (their declared scope), and
  others apply those writes.

| `kevy-replicate` | stone | AOF stream pub/sub over TCP; offset-based resume; initial snapshot ship; apply-side mutation queue | ~3 w |
| `kevy-elect` | stone | quorum ping; primary election on DOWN; topology change announcement | ~2-3 w (Phase 1.5) |
| `kevy-cluster-rw` | steel | topology discovery; read/write endpoint split; `READCONSISTENT` re-routing | ~1 w |
| `kevy-scope` | steel | scope = key-prefix declaration; ownership check; `-MISDIRECTED` reply | ~2 w (Phase 3) |
| `kevy-client-async` | steel | runtime-agnostic async surface; feature gates for tokio/smol/async-std | ~6 w (Phase 4) |

## Open questions

User-resolved 2026-06-18 except Q3 which stays deferred by user direction.

### Q1 · replication wire protocol — **locked: RESP3-extended**

Mutations are streamed as RESP3 `*N\r\n` arrays prefixed with an offset
marker. Pays a ~30 % framing tax vs a custom binary format but keeps
`tcpdump`-readability and zero new wire spec to maintain. Standard
RESP3 parsers (kevy-resp already there) decode it; debugging
replication lag becomes "show me the last frame on the wire".

Phase 1 task: define the exact frame shape (offset envelope + the
verbatim multi-bulk command). Leave room for the binary alternative
behind a feature flag if a measured pain point appears later.

### Q2 · initial snapshot ship — **locked: inline on the replication connection**

When a new replica handshakes, the primary streams the full snapshot
bytes on the same TCP connection, immediately followed by AOF tail
frames at the post-snapshot offset. The replica reads:

```
[snapshot bytes]    ← terminated by EOF marker / declared length
[offset N marker]
[AOF frame at N+1]
[AOF frame at N+2]
...
```

The replica buffers AOF frames arriving during snapshot read (if any)
and applies them only after snapshot is in. One connection, one
offset axis — no side-channel coordination, no "did the snapshot
finish before AOF started" race.

Phase 1 task: snapshot streaming format (length-prefixed vs delimited
+ checksum), buffering policy on the replica.

### Q3 · scope migration in Phase 3 — **deferred, user-coordinated**

`MOVE-SCOPE app:billing: from embed-A to embed-B`: drain in-flight
writes from A, ship the latest state, start B accepting, switch
clients. Three plausible shapes (quiesce-window, two-phase commit,
write-shadowing replay) all carry different operator UX.

**Locked direction**: this gets designed at the Phase 3 kickoff with
user coordination, not pre-decided here. The RFC commits only that
Phase 3 *has* scope migration; the mechanism is co-designed when we
get there.

### Q4 · async API shape — **locked: mirror + pipeline-first sugar**

`kevy-client-async` exposes both surfaces:

```rust
// a. Mirror — drop-in for blocking users
let mut c = AsyncConnection::open(url).await?;
let v = c.get(k).await?;

// b. Pipeline-first — single await for a batch
let (v1, v2) = c.pipeline()
    .get(k1)
    .set(k2, v2)
    .run().await?;
```

The mirror surface is the migration on-ramp (Connection → AsyncConnection
is grep-replace). The pipeline-first surface is where async actually
pays off — one TCP round-trip per batch, not per command. Both are in
the same crate, share the connection state machine, and the pipeline
form `.into_blocking()` degrades cleanly to blocking sequential calls.

Phase 4 task: pipeline command-set coverage (which commands are first-
class pipeline-able), behaviour on partial failures within a pipeline.

## Anti-scope (explicit non-goals)

- **No sharded multi-master.** Two writers may not own overlapping
  scopes. The trust model is "scopes are non-overlapping by design";
  config linter rejects overlapping prefixes. Cross-scope conflicts
  via misconfiguration are caught at startup, not resolved at runtime.
- **No cross-DC active-active with CRDTs.** Single DC, single
  partition assumption holds throughout v3. Cross-DC = different
  cluster, app-level federation.
- **No Raft.** F3 quorum is the cheapest correct primary election —
  no log replication, no leader leases. Sufficient for single-DC.
- **No online resharding.** Topology is config-declared, change
  requires a rolling restart of the affected nodes.
- **No TLS, no AUTH.** Same trust-bounded-network deployment model as
  single-node kevy (see `feedback-kevy-auth-tls-never.md`).
- **No tokio dependency in default `kevy-client`.** The async crate is
  separate; the default client stays 0-dep blocking forever.

## Q3 resolution — 2026-06-19, user-locked

**Choice: (a) quiesce-window.** `MOVE-SCOPE app:billing: from embed-A
to embed-B` runs as:

1. Operator issues `MOVE-SCOPE <prefix> from <A-node-id> to <B-node-id>`
   against any cluster member (the elect primary is the canonical
   recipient; non-primary members forward).
2. The cluster ownership table flips the prefix into `MIGRATING`
   state: `writer = A`, `target = B`. From this instant, A returns
   `-QUIESCED <prefix> migrating to <B-host:port>` to every write
   landing on this prefix (reads still work; new keys for OTHER
   prefixes A owns are unaffected).
3. A serialises the prefix's keyspace slice — only the keys
   matching `<prefix>` — via `kevy_persist::write_snapshot_to`
   (filtered iterator over the local store) and ships the bytes
   to B over a fresh control-plane TCP session (RESP2, single
   `MOVE-SCOPE-INGEST <prefix>` command carrying the snapshot
   bulk).
4. B applies the slice (under its existing replication apply
   path), confirms with `+ACK`.
5. The ownership table flips to `writer = B`, `MIGRATING` cleared.
   A drops its copy of the prefix's keyspace slice in a tick.
6. Clients see `-MISDIRECTED writer is B:<host:port>` on subsequent
   writes to the prefix; `kevy_cluster_rw` refreshes scope ownership
   and follows.

### Why (a)

- Matches the v3 anti-scope (no Raft / no gossip / no online
  resharding / no MIGRATE-ASK): the migration is operator-
  coordinated, has a deterministic outage window for one prefix,
  and never asks the cluster to coordinate concurrent writes
  across the cutover boundary.
- Scope migration is a rare ops action (quarterly+, not hot-path).
  The seconds-to-minutes write window matches the planned-
  maintenance posture; (b) two-phase commit and (c) write-
  shadowing only pay off when migrations are frequent.
- Single-direction recovery: every failure mode (operator abort /
  B crash mid-ship / network drop / B ACK timeout) reverts to
  "A still owns". No "two nodes both think they're the writer"
  state by construction.
- Operator UX is the simplest possible: one button, one progress
  signal, one terminal state. (b) and (c) require the operator
  to reason about "during cutover, some clients see A and some
  see B" — a 10× harder mental model for once-a-quarter work.

### Bounded outage

The write window equals `ship time = serialize(prefix-slice) +
network ship + B ingest`. For an `app:billing:` prefix in the
GB range over LAN this is single-digit seconds. Above that the
operator should reach for offline migration tools instead;
embed-as-writer is for keyspace partitioning, not multi-TB shard
splits.

### What `kevy-scope` ships

The Phase 3 plan's T3.2-T3.24 implement only this shape. Anti-
scope locked here for the remainder of v3:

- No write-shadowing during migration (no double-acceptance
  window).
- No 2PC across the cutover (no "prepare" state).
- No per-key streaming migration (no MIGRATE/ASK protocol).
- No automatic migration triggered by elect ANNOUNCE — the
  operator runs `MOVE-SCOPE` explicitly.

### Edge case: `MOVE-SCOPE` of an `embed-A`-owned prefix while A is dead

`F4` already covers this — the fallback server (declared in
`[[cluster.scope]] fallback = ...`) is the acting writer; the
operator runs `MOVE-SCOPE <prefix> from <fallback-id> to <B>`
against the fallback, which holds the data.
