# R2 设计轮(前半):窗口模型(R2a)与语义面(R2d)

> 研究总案 `2026-07-31-v5-research-master-plan.md` 的 R2 前半。**设计文档,非实现许可**——
> R2b(冷段形态)与 R2c(滑动机制)各自成 RFC 后半再定。
> 增补拍板生效:RDS 面不必 KV 纯洁(SQLite 类参照系合法);KV/pubsub 钉死超 valkey 水平;
> 架构 clean(新结构以石头/钢筋入场)。

## 一、取证:窗口要长的三个位置(现状 file:line)

1. **索引段** `kevy-index/src/segment.rs:46`:`Segment = BTreeSet<(IndexValue, key)> +
   back: HashMap<key, value> + value_counts + Option<RowValues>`;每条目 48B 结构开销
   (`ENTRY_OVERHEAD`)+ key/value 堆。**关键事实:tree 按 (value, key) 全序——若窗口列
   就是这个索引的 value,窗口边界 = 树上的一个 range 切点,出窗部分是一段连续前缀,
   天然可整段摘出转紧凑形态。**
2. **行** `kevy-store`:行 = hash key(`Value::Hash` / `SmallHashInline`),冷形态已有
   `Value::Cold(ColdRef)` 24B stub + vlog(per-key 记录,per-boot 重建)。
3. **温度决策** `kevy-store/src/tier_demote.rs`:预算水位 + LRU 采样(`sample_pick_with`),
   per-key 决策,无结构性边界;索引全热(floor 不可下沉,`reserved_bytes` 直接从
   demote 目标里扣除)。

现状的结构性短板,一句话:**温度是逐 key 猜出来的,不是结构里长出来的**——所以索引没法
跟着冷(索引条目没有"访问"概念),所以查询期永远不知道自己会不会踩冷(缓存未命中式的
延迟不可预测),所以 423MB 的索引 floor 一字节都省不下来。窗口模型就是把温度从"采样统计"
换成"值域结构"。

## 二、R2a:窗口模型三候选对抗

| | (i) 访问窗 | (ii) 时间窗(声明窗口列) | (iii) 键序窗 |
|---|---|---|---|
| 定义 | LRU 工作集的窗口化表述 | TABLE 声明 `WINDOW <col> <span>`,窗口 = 该列值域上的滑动区间 | 键的字典序单调段(消息 id / 订单号 / ULID) |
| 边界性质 | 统计的,逐 key | **值域切点,全局一致** | 键区间,per-prefix |
| 查询期可判定 | 否(永远可能 miss) | **是**——查询谓词与窗口边界都是同一列上的区间,编译期比较即知 命中热窗 / 跨窗 / 纯冷 | 是(键区间),但仅对按键访问 |
| 索引可段化 | 否(索引条目无访问概念) | **是**——窗口列被索引时是树 range 切点;其余索引经行归属间接段化(见 §四) | 部分(键在 tree 的 tiebreak 位,不连续) |
| 声明负担 | 零 | 一列一跨度(R4b 可自动建议) | 零(但依赖业务键惯例,不可靠) |
| 兜底能力 | **是**(现 tiering 即是) | 无声明时缺位 | 不可靠 |

**判据回摆**(总案 R2a:窗口边界必须查询期可判定——"没有缓存未命中概念"的前提):
只有 (ii) 完整满足。(iii) 是 (ii) 在"键即时间"业务里的投影,可作衍生优化而非模型;
(i) 不满足判据,但它已经存在(现 tiering),**保留为兜底层**。

**定稿假设(待实验检验)**:

> **窗口 = 声明的窗口列上的值域滑动区间。**
> `TABLE.DECLARE … WINDOW activity SPAN 90d` —— 窗口列必须是已声明的列;
> 窗口边界 `W = max_observed(activity) − span`(随写入自动滑动,滞回见 R2c);
> 行按窗口列值归属热窗/冷段;该表的索引段随之切段。
> 无 `WINDOW` 声明的表 = 现 tiering 行为不变(兜底层);
> KV 面(非 TABLE 键)= 现 tiering 行为不变(铁律一)。

两级温度的分工由此定形:**窗口是第一级(结构性:"应该冷"),预算水位是第二级
(保护性:"必须冷")**——窗口先把长尾结构性地移出内存,预算水位只处理"热窗仍超预算"
的过载态。tiering 不被替换,被叠加。

## 三、R2d:语义面

- **KV 面**:完全透明,零改动(铁律一的门禁语义:perfgate 对 valkey 赢线保持)。
- **TABLE 面**:
  - 声明可选:`WINDOW <col> SPAN <dur>`(窗口列须为 `i64` 类型的已声明列——时间戳、
    序号都是 i64;`f64`/`str` 窗口列首版拒绝并具名)。
  - **查询语义不变,延迟分层可观测**:跨窗查询默认合法(热段 + 冷段归并),回复不变;
    INFO/每查询计数暴露冷段触达数。`VERIFY` 增加窗口对账行(热窗行数 = 窗口区间内
    行数,双向)。
  - **编译期判定**是新的可陈述能力:`IDX.QUERY … RANGE a b` 与 `W` 比较,三种编译结果
    {hot-only, straddle, cold-only},查询计划(声明期意义上的)带上这个标签——
    这是给 R4b(自动声明)和运维观测的钩子,也是"超 PG 原理位"的可验证形态。
  - **窗口列写规则**(设计点,倾向严格):出窗行的窗口列**不可改写为窗内值**
    (= 行复活,需要显式 verb;类比 REPLACE 的"昂贵的事必须点名要求")。
    窗内改写自由。待 R4a 清单验证真实业务是否需要复活(如"重新打开旧订单")。

## 四、存储形态候选对抗(SQLite 授权后的新空间)

| | A. KV 合成(现状延伸) | B. row-native 表存 | C. 温度相变 |
|---|---|---|---|
| 热窗行 | hash key | 专门行格式(类型化) | **hash key(不变)** |
| 冷段行 | per-key vlog 记录 | 行存段文件(B-tree 页式) | **紧凑行段文件**(SQLite 页作冷段布局参照:槽页/溢出页,但只读、免 WAL) |
| 写路径 | 不变 | 分叉(HSET 不再是行写) | **不变**(热窗内全是今天的路径) |
| 4.x 承诺("行是 hash,写法不变") | 保 | **破** | 保 |
| 冷段与 R2b 冷索引段 | 两套形态 | 同构 | **同构(一套段基建)** |
| 冷读 | 逐 key pread | 页读 | 段内定位 + 邻近局部性(时间邻近的行物理邻近——窗口模型送的) |

**倾向 C(温度相变)**:热面保住 C4 铁律与 mailrs 式迁移故事(写法真的不变),
冷面拿到 row-native 的全部好处(紧凑、列感知、可压缩、可 mmap、备份=拷段文件),
且冷行段与冷索引段共用一套"段"石头(`kevy-seg`?)——架构 clean 铁律下,这块石头是
SQLite 参照系的落点:**学它的是只读段的页内布局与溢出处理,不学它的是 WAL/游标/VDBE**
(kevy 的写路径与执行形态自有模型)。B 不淘汰,记为"表从头 row-native"的 v-next 选项
(负结果档预留位)。

推论一条(值得单独说):**窗口模型让冷段免费获得聚簇**——出窗的行按窗口列值成批离场,
段文件天然按时间聚簇;"查上季度的订单"在冷段上是顺序读,这是 per-key vlog 结构性给不了的,
也是对 PG(堆表 + 索引随机访问)的又一原理位。

## 五、其他思路(发散区,按用户要求持续供给;每条一句可行性)

1. **分代类比**:窗口即 GC 分代(young=热窗 / old=冷段 / 复活=promotion)——借用分代
   不变式(old 不引用 young)来简化 VERIFY 的窗口对账。可行,叙事佳,机制上与 C 同构。
2. **三温层**:热窗(内存原生)/ **温段**(succinct 结构内存驻留:Elias-Fano 编码的
   有序键集,~2-4 bit/条目,回答存在性与范围计数)/ 冷段(磁盘)。温段让"跨窗 COUNT"
   不触盘。代价:一块新 succinct 石头;留作 R2b 的可选层。
3. **键模板**:`WINDOW` 声明时同时生成键模板(`row:{activity_bucket}:{id}`),让键序 =
   时间序,SCAN 即时间扫、shard 内物理局部性也对齐。代价:改写键 = 迁移成本,只适用新表;
   记为 R4c 迁移工具的选项而非核心。
4. **冷段即备份**:段文件不可变 ⇒ 备份增量 = 新段文件;`备份=拷文件` 升级为
   `增量备份=拷新段`(S5 乘法)。零额外机制,R6 直接收。
5. **观察先行的窗口建议**(R4b 前置):无 WINDOW 的表跑访问-窗口列相关性统计,
   `TABLE.ADVISE` 输出"97% 查询谓词落在 activity 最近 14d,建议 WINDOW activity SPAN 30d"。
   把 S3(没有 DBA)与声明负担的张力交给引擎解。

## 六、非窗口列索引怎么段化(开放问题,R2b RFC 的第一题)

窗口列上的索引天然切段(§一.1);**其余索引**(email unique、dept range)条目无窗口值。
候选:(a) 冷行的索引条目随行出窗进该索引的冷段(按行归属,需要 value→窗口归属查询——
back map 有 key,key 可判窗?只有行在才能判…);(b) 非窗口索引保持全热(接受部分 floor);
(c) 复合进窗口列(`ORDERPATH ON dept THEN activity` 型天然可段)。取舍数据待 R4a 清单
(真实业务的非窗口索引占比)——**不预设,进 R2b**。

## 七、本轮小结与下一步

- R2a 定稿假设:窗口 = 声明窗口列的值域滑动区间;两级温度(窗口结构性 + 预算保护性)。
- R2d 定稿假设:KV 全透明;TABLE 声明可选、语义不变、延迟分层可观测、编译期三态标签。
- 存储形态倾向:C 温度相变 + 统一"段"石头(SQLite 只读段布局作参照)。
- 交 R2b:冷段形态(行段 + 索引段 + §六非窗口索引)与温段可选层;交 R2c:滑动/滞回/
  持久化交互;等 R4a 清单回来校验 R2d 的复活规则与 §六 的取舍。
