# v5 arc 设计输入 —— 从模型出发(pre-RFC;待用户拍板)

**愿景(用户拍板 2026-07-26)**:kevy 做**中小型系统的 datasolution**,在中小型 RDS 业务上
全面超越 PG。

**方法纪律(用户同日纠正)**:不做"攻击优化"。先按自己的模型设计出最适合自己的路径、
做足优化、打磨到**设计/原理/算法/模型四层都没有空间**,然后才去对比;只有自身空间确实
穷尽仍有差距,才允许针对性优化。→ **本文件不含任何"追平某个外部数字"的目标。**
外部实测(`bench/PGCOMPARE-2026-07-26.md`)在此只作**现状体检单**。

## 0. 模型是什么(设计的出发点,不是约束清单)

kevy 的模型有五条互相咬合的性质。任何 v5 设计的第一检验是**它是否让这五条更自洽,
而不是更多例外**:

| # | 性质 | 现状 |
|---|---|---|
| M1 | **share-nothing / 每核一分片** | 无锁、无共享可变状态;并发靠分片而非互斥 |
| M2 | **一切按 key 路由到属主分片** | 一次请求一跳;这是点查快的全部原因 |
| M3 | **derived-by-construction** | 索引/视图在写路径同步维护,永不漂移,可从数据重建 |
| M4 | **冷热窗口** | RAM 预算 + 冷值下沉 vlog;**索引层 100% 常驻 RAM** |
| M5 | **纯 Rust / 零依赖** | 无第三方分配器、无压缩库;OS 边界集中在 kevy-sys |

## 1. 现状体检:模型内部的一处不自洽

`bench/PERF-DECOMP-2026-07-26-idx-fanout.md`(变分片数、`pk` 作对照):

| 分片数 | pk p50(对照) | idx p50 | page p50 |
|---:|---:|---:|---:|
| 1 | 15 µs | **36 µs** | **43 µs** |
| 16 | 22 µs | **140 µs** | **157 µs** |

对照组持平 = M2 成立;索引查询随分片数劣化 3.9×,**16 分片下 74% 的延迟是扇出**。

根因不是低效,是**维度错配**:索引跨整个键空间,而键空间按**行键**分区,查询却按**索引值**
到达 → 任何分片都可能有命中 → 必须问全场。

> **`IDX.QUERY` 是这个引擎里唯一不遵守 M2 的操作。**

这不是"输给谁"的问题,是**模型自身的一处特例**。消掉它,M1/M2/M3 会更自洽。

## 2. 模型自问(设计轮的题目,不是候选清单)

### Q1 — 在一个一切按 key 路由的引擎里,索引本来应该是什么?

若索引项**本身就是键**(如 `idx:sku:42` 持有匹配行的引用),则:
- 索引查询按同一条规则路由 → 一跳 → **M2 恢复完整,特例消失**
- 写一行要更新**另一个分片**上的索引项 → 写从"本地"变"跨分片"

**要回答的**:M3(同步维护、零漂移)能否在跨分片下保持?引擎已有的 xshard dispatch /
escrow / outbox / CDC feed 是否够用?**代价必须与写路径的现有优势一起量。**

### Q2 — 访问路径该不该也有冷热窗口?

M4 给行做了冷热窗口,但**索引层常驻 RAM 是一个决定,不是物理必然**。实测:200 万行
2 索引 = 427 MB 常驻;1200 万行的 12GB 场景 = 613 MB。对"中小型系统"这个愿景,
索引常驻是否是最优?一个访问路径的哪些部分**必须**在 RAM(定位结构),哪些可以下沉
(叶子/postings)?

### Q3 — 索引的分片粒度应该由谁决定?

现在分片数是全局的(`--threads`)。v1.30 的 `--accept-shards` 已证明"少而密"在某些
形状上更优(+10.6%)。**同一个引擎里,不同的数据/访问路径能不能有不同的分片度?**
这是 M1 的自然延伸还是破坏?

### Q4 — 零依赖前提下,存储表示还有多少空间?

体检显示 PG 的 TOAST 压缩在重复负载上省 25×,kevy 无值压缩(M5 所致)。
**自研、零依赖、且与冷热窗口协同**的表示优化(定长编码 / 列式化 VALUES / 页内压缩)
是否属于模型自然形态?——注意这条要放在 Q1-Q3 之后:体检显示当前主项不在这里。

### Q5 — 中小型系统真正的形状是什么?

愿景说"中小型"。这应当**改变设计判据**:单机、核数有限、数据量有界、运维人少。
在这个前提下,什么该被优化(启动时间?内存下界?单连接延迟?运维面?),
什么可以不做(跨机分片已明确 out-of-scope)?**这条应当先于 Q1-Q4 定调。**

## 3. 我的建议顺序(非拍板)

1. **先定 Q5**(中小型的设计判据)—— 它决定其余四问的权重。
2. **再做 Q1 的设计轮** —— 它是唯一"消特例"的问题,且体检指向它是当前主项。
   产物 = RFC,含 M3 保持性论证 + 写路径代价的**预算表**(不是实测,是设计期估算)。
3. **Q2 与 Q3 并行探索**(都可先做 read-only 拆解,不需实现)。
4. **Q4 最后** —— 表示层优化在前三者定形后才知道该服务于什么。
