# v5 arc 设计输入 —— 愿景已变,约束解锁(pre-RFC;待用户拍板)

**愿景(用户拍板 2026-07-26)**:kevy 做**中小型企业(SME)的 datasolution**,在中小型 RDS
业务上全面超越 PG。**"中小型"指企业规模,不是数据规模** —— SME 的数据可以是几千万行、
几十 GB;稀缺的是**运维人力、专家与硬件预算**。

**约束状态(用户同日)**:**v5 设计不受既有项目约束限制,因为 vision 变了。**
凡是为旧愿景("纯 Rust 零依赖的 Redis 兼容 KV")而锁的决定,在本 arc 里都是**设计变量**。

**方法纪律(用户同日)**:不做"攻击优化"。先按自己的模型设计到位、打磨到设计/原理/算法/
模型四层都没有空间,再去对比。→ 本文件**不含**任何"追平 PG 某数字"的目标;
`bench/PGCOMPARE-2026-07-26.md` 在此只作**现状体检单**。

---

## 1. SME 判据(愿景的直接推论,排在一切之前)

稀缺的是人和钱,不是数据。按对 SME 的分量排序:

| # | 判据 | 含义 |
|---|---|---|
| **S1** | **内存即金钱** | RAM 是 SME 最贵的资源。把"加内存"变成"加磁盘"是 10–50× 的成本差 |
| **S2** | **一个东西,不是一套栈** | 替掉 PG + Redis + 搜索 + 队列,而不是做其中之一 |
| **S3** | **没有 DBA,也没有 SRE** | 不调优、不 vacuum、不看执行计划——**也包括不配 TLS 终端、不设计网络隔离** |
| **S4** | **普通机器** | 4–16 核、8–64 GB、一台机 |
| **S5** | **运维面小** | 一个二进制、一份配置、备份=拷文件、升级=换二进制 |

## 2. 模型:哪些是思想固有的,哪些只是历史约束

上一版把五条并列成"模型",这是错的——它们的处置完全不同。

### 2a. 思想固有(动它们就不是 kevy 了)

| | 性质 | 为什么固有 |
|---|---|---|
| **I1** | share-nothing / 每核一分片 | 无锁并发的来源;点查 71 µs 赢 PG 2.8× 全靠它 |
| **I2** | 一切按 key 路由到属主 | 一请求一跳。**目前 `IDX.QUERY` 是唯一的例外** |
| **I3** | derived-by-construction | 写路径同步维护、永不漂移、可从数据重建 —— **这正是 S3(没有 DBA)的技术实现** |
| **I4** | 冷热窗口 | 让"数据量"与"内存预算"解耦 —— **S1 的现有答案** |

### 2b. 历史约束(为旧愿景而锁,现在是设计变量)

| | 约束 | 它保护的东西 | 解锁后对 SME 判据的意义 |
|---|---|---|---|
| **C1** | **零依赖**(L2 锁定) | 供应链、构建简单、体积 | **直接买到 S1**:换分配器可消掉 RSS/逻辑值 2.24× 的碎片(已证明 `malloc_trim` 与 arena 上限均无效);引入压缩可拿到重复负载上 ~25× 的存储差(PG TOAST 实测) |
| **C2** | **Law 3**(写着"永不"越过 RDS 事件视界:无查询语言、无 planner、无 join) | 延迟可预测、无执行计划意外 | **这是替代 PG 的最大门槛**。它与 S3 的关系是**双向的** —— 见 §3 |
| **C3** | **AUTH / TLS 明确 OUT**(原文:"不要放进 backlog/roadmap") | 引擎保持纯粹;安全交给网络层 | **与 S3 直接冲突**。"放到私网后面"假设 SME 有网络工程能力;没有 SRE 的公司拿到一个无鉴权的数据端口,是产品缺陷而不是干净设计 |
| **C4** | RESP / Redis 兼容 | 每种语言都有现成客户端(S2/S5 的分发优势) | 仍是资产,但不再是数据模型的天花板 |
| **C5** | no_std / MCU 端口 | 边缘设备 | 与 SME 愿景无关,可不再作为设计约束 |

## 3. 核心张力:Law 3 与"没有 DBA"是双向的

Law 3 的理由是:**声明式访问路径 = 延迟可预测 = 不需要 DBA**。
但对 SME 它同时意味着:**你必须预先知道自己要查什么** —— 这恰恰需要 DBA 级的前瞻。

> S3 既支持 Law 3(不必调优),又反对 Law 3(要求前瞻)。

**模型自己给出的第三条路**(不是抄 planner):把"声明"从人转移到引擎 ——
**引擎观察真实查询,自动声明访问路径**,而不是在查询时临场决定计划。

- 保住 I3:路径依然是被声明的、写路径同步维护的、可预测的
- 消掉门槛:SME 不需要预先知道要查什么
- 与 planner 的本质区别:**决定发生在声明期(一次),不在查询期(每次)** ——
  延迟仍然没有执行计划意外
- `kevy-sql` 已经做了一半(声明期编译 + "缺哪个索引"的具名报错),差的是**自动闭环**

这是本 arc 最值得设计的东西,而且**它是模型的自然形态,不是对 PG 的模仿**。

## 4. 体检数据在 SME 判据下的重读

上一版把"索引查询扇出"当主项。**按 SME 的机器重读,这个结论要翻**:

| 分片数 | idx p50 | vs PG(132 µs) |
|---:|---:|---|
| 4 | 48 µs | **kevy 快 2.8×** |
| 8 | 71 µs | **kevy 快 1.9×** |
| 16 | 140 µs | kevy 慢 1.1× |

> **在 SME 的 4–8 核机器上,索引查询 kevy 本来就赢。扇出是 16 核放大出来的问题。**

而**内存差距在 SME 上是直接的钱**:1 GB 数据贵 9.8×;12 GB 分层后仍贵 4.5×。
一台 32 GB 的机器能装多少业务,由这个比值决定。

## 5. 建议顺序(非拍板)

1. **S1 战役 —— 每 GB 数据的内存成本**(解锁 C1 后空间最大)
   分配器(直接消 2.24× 碎片)· 值压缩 · 索引层的冷热窗口 · 表示优化。
   SME 判据下唯一的第一优先。
2. **C3 决定 —— 鉴权 / 传输安全**(S3 的硬缺口;先要你拍做不做,再谈设计)
3. **§3 的自动声明闭环**(模型价值最高,且直击 Law 3 的采用门槛)
4. **I2 的特例消除(索引即键)** —— 模型最干净,但 SME 机器上收益最小,放后面
5. 分片粒度(与 4 相关,可并入)
