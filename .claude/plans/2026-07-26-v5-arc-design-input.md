# v5 arc 设计输入 —— 中小企业的 datasolution(pre-RFC;四项约束已拍板)

**愿景(用户拍板 2026-07-26)**:kevy 做**中小型企业(SME)的 datasolution**,在中小型 RDS
业务上全面超越 PG。**"中小型"指企业规模,不是数据规模** —— SME 的数据可以是几千万行、
几十 GB;稀缺的是**运维人力、专家与硬件预算**。

**方法纪律(用户同日)**:不做"攻击优化"。先按自己的模型设计到位、打磨到设计/原理/算法/
模型四层都没有空间,再去对比。→ 本文件**不含**任何"追平 PG 某数字"的目标;
`bench/PGCOMPARE-2026-07-26.md` 在此只作**现状体检单**。

## 0. 四项约束的拍板结果(用户 2026-07-26)

| | 问的是 | **拍板** | 对设计的实际后果 |
|---|---|---|---|
| **C1** | 零依赖是否放弃 | **铁律保持。自研,学习先进开源项目,只能做得更好** | 内存战役照打,但**分配器与压缩必须自研**——这把"换个 crate"变成两块**石头**(见 §4) |
| **C2** | Law 3 是否松动 | **自己主动因为 vision 改是可以的** | 松动的合法性来自**模型自身的推导**,不来自"PG 有所以我们也要" |
| **C3** | AUTH / TLS 是否进 v5 | **先不做,外层 caddy / nginx 包裹即可** | S3 的这一格由**部署配方**回答,不由引擎回答(见 §5) |
| **C4** | RESP 是否仍是硬约束 | **不冲突。KV 用法完全不变也不应该退化,pubsub 同** | 升级为**硬不变式**:v5 任何内存/分层改动,KV 与 pubsub 不得退化(见 §6) |

## 1. SME 判据(愿景的直接推论,排在一切之前)

稀缺的是人和钱,不是数据。按对 SME 的分量排序:

| # | 判据 | 含义 |
|---|---|---|
| **S1** | **内存即金钱** | RAM 是 SME 最贵的资源。把"加内存"变成"加磁盘"是 10–50× 的成本差 |
| **S2** | **一个东西,不是一套栈** | 替掉 PG + Redis + 搜索 + 队列,而不是做其中之一 |
| **S3** | **没有 DBA,也没有 SRE** | 不调优、不 vacuum、不看执行计划 |
| **S4** | **普通机器** | 4–16 核、8–64 GB、一台机 |
| **S5** | **运维面小** | 一个二进制、一份配置、备份=拷文件、升级=换二进制 |

## 2. 模型:哪些是思想固有的

| | 性质 | 为什么固有 |
|---|---|---|
| **I1** | share-nothing / 每核一分片 | 无锁并发的来源;点查 71 µs 赢 PG 2.8× 全靠它 |
| **I2** | 一切按 key 路由到属主 | 一请求一跳。**目前 `IDX.QUERY` 是唯一的例外** |
| **I3** | derived-by-construction | 写路径同步维护、永不漂移、可从数据重建 —— **这正是 S3(没有 DBA)的技术实现** |
| **I4** | 冷热窗口 | 让"数据量"与"内存预算"解耦 —— **S1 的现有答案** |
| **I5** | **纯 Rust 自研(C1)** | 拍板后从"约束"升为**固有**:每一层都是自己的,才有每一层都能打磨的可能 |

## 3. 核心张力:Law 3 与"没有 DBA"是双向的

Law 3 的理由是:**声明式访问路径 = 延迟可预测 = 不需要 DBA**。
但对 SME 它同时意味着:**你必须预先知道自己要查什么** —— 这恰恰需要 DBA 级的前瞻。

> S3 既支持 Law 3(不必调优),又反对 Law 3(要求前瞻)。

**模型自己给出的第三条路**(不是抄 planner):把"声明"从人转移到引擎 ——
**引擎观察真实查询,自动声明访问路径**,而不是在查询时临场决定计划。

- 保住 I3:路径依然是被声明的、写路径同步维护的、可预测的
- 消掉门槛:SME 不需要预先知道要查什么
- 与 planner 的本质区别:**决定发生在声明期(一次),不在查询期(每次)** ——
  延迟仍然没有执行计划意外
- `kevy-sql` 已经做了一半(声明期编译 + "缺哪个索引"的具名报错),差的是**自动闭环**

C2 拍板("自己主动因为 vision 改是可以的")正是给这条路的授权:它的正当性来自模型推导,
不是来自模仿 PG。

## 4. S1 内存战役 —— C1 保持之后,它变成两块石头

C1 不放弃,不意味着 S1 让步;意味着**买不来的要自己造**。两项都符合石头判据
(零业务耦合、可 semver、可独立 fuzz/bench),也正是"学习先进开源、只能做得更好"的落点:

- **`kevy-alloc`** —— 已实测的 2.24× RSS/逻辑值碎片,`malloc_trim` 与 arena 上限**都证明无效**
  (glibc brk 堆对 sub-mmap-threshold 的 churn 不可回收)。这不是调参能解的,要**自己的分配器**:
  尺寸分级、per-shard 无共享 arena(与 I1 天然同构)、可归还给 OS 的段管理。
  参照系:mimalloc / jemalloc / tcmalloc 的公开设计。
- **`kevy-compress`** —— PG 的 TOAST 在重复负载上省了 25×(实测),kevy 目前**没有值压缩**。
  分层已把冷值放到 vlog,压缩与它是乘法关系(冷值压缩比 = 磁盘容量倍数)。
  参照系:LZ4 / zstd 的块格式与熵编码。

> C1 让这条路更长,但也让它更彻底:分配器可以**为 kevy 的分配形状**设计
> (每分片独占、值尺寸分布已知、冷热迁移是已知事件),这是通用分配器做不到的。
> "只能做得更好"在这里有具体含义 —— 通用性换专用性。

另两项不需要新石头:索引层的冷热窗口(I4 推广到访问路径)、值表示优化。

## 5. C3 的处理:S3 那一格由部署配方回答

用户拍板"先不做,caddy / nginx 包裹即可" —— 那么 v5 欠 SME 的不是引擎代码,
而是**一份可照抄的、不需要 SRE 的部署配方**(反代 + TLS 终端 + 只暴露必要端口),
并写进 docs 与站点。引擎侧保持 `feedback-kevy-auth-tls-never` 不变。

## 6. C4 升级为硬不变式(gate 义务)

"KV 用法完全不变也不应该退化,pubsub 也一样" —— 这是可断言的,因此它进门禁而不是进文档:

- 自研分配器落地后:**perfgate 的 KV 线与 pubsub 线必须在既有容差内**,不是"新功能关掉时不退化",
  而是**打开时也不退化**(分配器没有"关掉"这一说)
- 值压缩:热值路径必须证明零成本(体裁参照 tiering 的 A1 "热值路径只多一个永不命中的 match 臂")
- 这条与 v4 capacity arc 的 A1/A2/A3 同源,直接扩写即可

## 7. 体检数据在 SME 判据下的重读

上一版把"索引查询扇出"当主项。**按 SME 的机器重读,这个结论要翻**:

| 分片数 | idx p50 | vs PG(132 µs) |
|---:|---:|---|
| 4 | 48 µs | **kevy 快 2.8×** |
| 8 | 71 µs | **kevy 快 1.9×** |
| 16 | 140 µs | kevy 慢 1.1× |

> **在 SME 的 4–8 核机器上,索引查询 kevy 本来就赢。扇出是 16 核放大出来的问题。**

而**内存差距在 SME 上是直接的钱**:1 GB 数据贵 9.8×;12 GB 分层后仍贵 4.5×。
一台 32 GB 的机器能装多少业务,由这个比值决定。

## 8. 建议顺序(拍板后收敛;仍待你确认)

1. **`kevy-alloc`** —— 唯一第一优先。碎片是**已实测、已排除调参解**的确定项,
   且它对 KV / pubsub / 索引 / 分层**全线受益**,不挑负载
2. **`kevy-compress`** —— 与 I4 相乘;先冷值(vlog 内),热值另行判断
3. **§3 的自动声明闭环** —— 模型价值最高,C2 已授权
4. **索引层冷热窗口**(I4 推广到访问路径)
5. **I2 的特例消除(索引即键)** —— 模型最干净,但 SME 机器上收益最小
6. C3 的部署配方文档(小,可并行)
