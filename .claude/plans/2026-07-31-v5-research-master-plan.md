# v5 研究总案 —— 滑动窗口热区的 KV,合成虚拟 SQL support

> **地位**:研究组织文档,`2026-07-26-v5-arc-design-input.md`(S/I/C 判据)的下游、
> 各研究单元 RFC 的上游。**任何单元开工前仍需自己的 RFC**(实现需 RFC 先行,拍板 2026-07-26)。
>
> **主轴(用户拍板 2026-07-31)**:用**滑动窗口热区的 KV** 来实现**虚拟 SQL support**。
> 最终合成目标:kevy 的模型在**中小企业级别的 RDS 专业性与性能上超过 PG18**。
>
> **纪律(继承,全文有效)**:这是 v5 的一次尝试,不是 v5;从原理起都可调;负结果留档
> (v8 ledger 体例);不设版本号目标;验收线写**结构性陈述**,数字是推论——
> **禁止把"比 PG 快 X%"当任何单元的验收线**,`bench/PGCOMPARE-*.md` 只是体检单;
> KV + pubsub 不得退化(C4,gate 义务);零依赖铁律(C1);单机(S4)。

---

## 0. 主轴一句话展开

SME 的 RDS 负载有形状:**操作面集中在近期数据**(订单、消息、会话、告警),历史是长尾。
PG 用 buffer pool 对付这个形状——通用页缓存,查询期每次重新发现热点。
kevy 的模型答案是把这个形状**做成结构**:

- **热区是一个滑动窗口**——工作集所在的窗口常驻内存,以内存原生结构(不是页缓存)服务;
  窗口随业务自动滑动,旧数据(行**与索引段**)出窗下沉,新数据进窗。
- **虚拟 SQL 是窗口之上的合成**——TABLE / IDX / VIEW / kevy-sql 已有的声明期编译路线不变
  (Law 3:决定在声明期,查询期没有计划意外),SQL 的专业性面(子集覆盖、迁移、备份、
  可验证性)由 KV 原语 + 窗口分层合成,不做 SQL 引擎。

对着 PG 的结构性差异(这是合成论证的骨架,不是数字目标):
PG 在每次查询时用通用缓存逼近工作集;kevy 把工作集声明成窗口结构,窗口内没有"缓存未命中"
这个概念,窗口外是显式的、可计数的冷路径。前者的上界是缓存命中率,后者的上界是内存原生
结构的速度——这就是"模型能超过"的原理位。

## 2. 各单元:问题 / 已知 / 假设 / 判据 / 实验形态

### R1 — `kevy-alloc`(进行中,接住点 = v8 收口 ledger)

- **问题**:glibc brk 堆对 sub-mmap-threshold churn 的碎片(实测 2.24× RSS/逻辑值)
  调参无解;分配器要为 kevy 的形状自研(per-shard 无共享、值尺寸分布已知、冷热迁移是已知事件)。
- **已知**(v8 ledger):mmap_lock 真凶已修;12 角 7 过;M3 常驻 1.98× vs glibc 2.40×;
  **residual = 集合写小分配元数据远线**(hset 17.3% vs 10.1%),天真修法已知破坏 M3。
  八个死机制留档。
- **下一步**:residual 的设计轮(不是继续 polish——两轮不动针即 decomp 的纪律仍适用)。
- **结构性判据**:常驻/逻辑值比值的组成可解释(每一项开销名字、scale 方式);
  KV/pubsub perfgate 既有容差内(C4)。
- **与主轴的关系**:窗口滑动 = 持续的分配/释放churn,分配器是它的地板;但 R2 不等 R1。

### R2 — 滑动窗口热区(主轴核心,开研第一单元)

现状 tiering 是**预算水位 + LRU 采样**:demote 到 `budget·19/20 − floors`,索引全热(floor
不可下沉)。滑动窗口是它的演化:热区由**窗口**定义,窗口随业务滑动,**索引段也随窗口冷热**。

拆四个子问题,各自可独立试验、可独立翻盘:

- **R2a 窗口模型**:窗口由什么定义?候选:
  (i) 访问窗——现 LRU 的窗口化表述;(ii) 时间窗——按行的某个时间属性(activity 列)
  声明;(iii) 键序窗——利用 SME 业务键常见的时间单调性(消息 id、订单号)。
  S3(没有 DBA)⇒ 窗口**必须能自动**;(ii)/(iii) 给出**可预测的窗口边界**
  (查询能在声明期知道自己是否跨窗——Law 3 的延伸),(i) 只有统计边界。
  **假设**:(ii)/(iii) 型窗口 + (i) 兜底的混合是对的;**判据**:窗口边界对查询期可判定
  (一个查询在编译期就知道它命中热窗、跨窗、还是纯冷),这是"没有缓存未命中概念"的前提。
- **R2b 索引段窗口化**(原 T5"可下沉索引层"的落点):索引按窗口分段——热窗段常驻
  (今天的全部结构),出窗段转为**冷段**(紧凑只读形态:排序数组/mmap/压缩,candidates:
  与 R5 相乘)。查询:窗口内 = 今天的路径;跨窗 = 热段 + 冷段归并(显式、可计数)。
  **已知包袱**:index floor 是消费者实测的第一内存项(text 索引 423MB/1.09GB);
  这是对 S1(内存即金钱)分量最重的单元。
  **判据**:冷段的内存成本公式化(≪ 热段/条目);跨窗查询的冷读次数有公式
  (段数 × O(log) 而非 O(条目));**热窗内查询与无窗口时 byte-identical**(A5 体裁)。
- **R2c 滑动机制**:出窗/进窗是持续小迁移,不是搬家事件。tick 收敛纪律(4.1-V5 的
  "idempotent is not convergent" 是这里的前置学费——滑动的 idle 态必须近零);
  迁移与 AOF/replay/reshard 的交互(vlog 前例:流式、pin、不 promote);
  窗口边界抖动的滞回。**判据**:滑动的稳态成本 ∝ 进出窗速率,与窗口内容量无关。
- **R2d 语义面**:窗口对用户可见吗?候选:完全透明(所有查询语义不变,只有延迟分层)
  vs 可声明(TABLE 声明窗口列,跨窗查询要显式说)。C4 硬约束:KV 面完全透明是底线;
  TABLE 面的选择是 R4 的输入。**假设**:透明为默认 + 声明可选("这张表按 activity
  开 90 天窗")是对的——声明版给出可预测性,透明版给出零门槛。

**R2 总判据(结构性)**:一台 S4 机器(8-64GB)承载"数据 ≫ 内存"的 TABLE 负载时,
剩余的内存组成 = 热窗(∝ 工作集)+ 冷段元数据(公式化的小项)+ stub;
每一项的 scale 方式可陈述。**这台机器上"能装多少业务"由工作集决定,不由数据量决定**
——这是 S1 的终局陈述。

### R3 — 热窗内查询路径

- **问题**:窗口保证数据在内存后,查询路径本身就是上界。体检单靶子:索引查询/分页
  PG 快 2.2×/1.9×,**慢在查询路径不在 I/O**;SME 4-8 核上 kevy 已赢(48µs/71µs vs 132µs),
  16 核扇出放大(140µs)——扇出治理(I2 特例消除:索引即键、单跳)在 SME 收益小但模型干净。
- **已知前科**:FTS pass-1 会计开销 `docs()` 窄入口 term -88%/phrase -73%——同类"会计税"
  在 scalar 查询路径大概率同在;decomp 方法论(两轮 polish 不动针 → 18 段拆解)直接适用。
- **实验形态**:对 idx_query/分页/hydration 做 Phase A decomp(读 PG18 执行器等价路径作参照系),
  Top-N attacks;**先过双 gate**(baseline variance + perf-record 攻击面 ≥ 双位数 pp)。
- **判据**:热窗内一次分页查询的成本组成 18 段可陈述且 ±20% 对账实测。

### R4 — 虚拟 SQL 专业性面

- **R4a 覆盖度清单**:从三个真实来源提炼"SME RDS 到底用什么":mailrs 迁移(14 轴、
  membership 行、8 课)、smix、`docs/rds-workloads.md` 的对应表 + spg 项目的 SQL 面经验。
  产物:**SQL 形状清单**,每项标注 {已有 | 引擎缺 | 配方 | 拒绝并有替代}。
  重点悬案:join 形状的覆盖(VIA + membership 行够不够真实业务)、聚合窗口
  (GROUP BY 已有 agg;窗口函数?)、多语句事务的边界、约束(verify-not-enforce 路线的极限)。
- **R4b 自动声明闭环**(设计输入 §3 的第三条路,C2 已授权):引擎观察真实查询 →
  **自动声明**访问路径(决定在声明期,一次;不是查询期 planner)。研究点:观察什么
  (被拒绝的查询即需求信号——kevy-sql 已会报"缺哪个索引")、谁批准(自动建 vs 建议给人)、
  回收(不再用的路径)。与 R2 的合成点:**自动声明的窗口**——观察到查询只打近期就自动收窄。
- **R4c 工具链**:kevy-sql schema 编译已有;迁移工具(pg_dump → kevy 的路)、
  查询卡片的覆盖度。**专业性 = 迁移那天的体验**,mailrs 八课是需求文档。
- **判据**:清单上每一项有归属与理由;自动声明闭环有"从未见过的业务负载,零人工声明,
  N 分钟后全部查询有访问路径"的实验形态。

### R5 — `kevy-compress`(RFC 已有)

- 冷值压缩与窗口是乘法:出窗值的压缩比 = 磁盘容量倍数,也是冷段索引(R2b)的候选形态。
- prior art 已核:`spg_crypto::lzss`(356 LOC no_std,生产中)可学不可依(C1);
  参照系 LZ4/zstd 块格式。
- **判据**:热路径零成本证明(A1 体裁);压缩比/解压速度对 SME 负载(文本重)的包络。

### R6 — SME 运维面(S3/S5,收口期单元)

- 备份 = 拷文件(AOF/快照语义已有,窗口/vlog 加入后**要重新陈述**——冷段文件进不进备份面);
  升级 = 换二进制(降级窗口可读的先例);部署配方(C3:caddy 包裹,文档 + 站点);
  可验证性叙事(VERIFY/`missing` 已被消费者实证"最想要而没有的"——这是对 PG 的**专业性差异化**:
  PG 的索引不需要验证因为它没有第二真相,kevy 的 derived-by-construction + VERIFY 是
  "没有 DBA 也能确信"的答案,写进对外叙事)。
- **判据**:S5 的五句话(一个二进制/一份配置/备份拷文件/升级换二进制/不调优)在窗口化后
  每句仍然为真,且有 e2e 背书。

### R7 — 合成与对比方法论(常设)

- **体检单节奏**:PGCOMPARE 只在单元收口后重跑(对比在打磨之后,不作设计输入);
  每次体检单固定轴 + 机器形状(S4:4-8 核档)。
- **perf 纪律**:2 轮 polish 不动针 → decomp;§1 触发词黑名单;Phase A/B 双 gate。
- **升格判据**(什么时候"尝试"配得上叫 v5):R2 总判据成立 + R3 的 18 段对账 +
  R4a 清单无"引擎缺"的红项 + R6 五句话为真 + C4 门全绿——此时才做终局对比,
  终局对比覆盖**专业性与性能两面**(体检单轴 + mailrs 式全量迁移 dogfood 第二轮)。

## 3. 合成路径(单元怎么拼起来)

```
R1 alloc(地板)──┐
R5 compress(乘法)─┤
                  ├─ R2 滑动窗口热区(结构主轴)
                  │      └─ R3 热窗查询路径(窗口内的速度上界)
R4 虚拟 SQL 面 ───┘      └─ R2b 冷段(窗口外的容量上界)
                  └─ R6 运维面(合成后的 SME 收口)
                  R7 方法论贯穿
```

终局形态一句话:**声明一张带窗口的表,业务只管写;工作集自动留在热窗内以内存原生结构
服务,历史自动出窗成紧凑冷段;查询在编译期就知道自己踩在窗口的哪一侧;VERIFY 随时证明
一切没漂;这台 8GB 的机器装下了 200GB 的业务**——每个从句对应一个研究单元的判据。
